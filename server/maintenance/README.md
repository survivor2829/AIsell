## 用户流程

测试安装版启动和每 6 小时检查更新，校验签名后后台下载。下载完成后显示提示，正常关闭软件时安装，也可以点击“退出并更新”。退出沿用应用原有任务清理流程；更新前保存编辑内容并结束工作任务。

当前开发版在“吐槽中心 → 日志诊断”保留“自动上传脱敏诊断”，默认关闭。开启后只传版本、随机安装编号、模块、事件、错误码及有限技术字段；不传原始消息、堆栈、联系人、路径、密钥、图片或素材。网络失败保留本地队列，最多 200 条、30 天，退避重试；关闭即清空待传队列。已经上传的记录最多保留 30 天。服务器另设 5 万条上限。

“我要吐槽”单独保存 1～2000 字正文、分类和可选任务关联，默认勾选仅本次附带近期脱敏诊断，可关闭。提交时固定内容和最多 20 条白名单异常，独立队列先持久保存再发送；收到有效回执后，“我的反馈”才显示待处理、处理中或已解决。回执凭据由当前 Windows 用户加密保存，重试保留同一 ID、内容及凭据。反馈服务暂未部署时，404 会停止自动重试并保留内容，服务上线后用户可手动重新发送；不会切换持续自动上传开关。

顶栏公告复用 `/v1/releases/{channel}/latest` 的签名清单。客户端每 30 分钟及打开公告时仅刷新元数据，本机缓存最近收到的 20 条和已读状态；这不是服务端全量公告历史接口，首次安装也不会补取此前所有版本。手动刷新公告不会触发安装包下载，原每 6 小时的更新检查仍独立执行。离线教程随客户端提供，不依赖此服务。

诊断后台可看异常聚合、版本运行记录、近期详情，可标记排查中或修复版本。修复版本及更高版本出现新的同类异常时重新打开问题。数据只覆盖开启诊断的客户端，不能据此断言所有客户无故障；事件详情最多展示最近 200 条。

## 访问后台

在本机 `desktop/` 运行 `node scripts/open-maintenance-admin.cjs`，然后打开 <http://127.0.0.1:18081>。脚本窗口保持运行。后台只监听服务器回环地址 `127.0.0.1:8081`，云防火墙无需开放 8081。SSH 私钥只留本机。

公网 HTTPS 443 的现有服务提供健康状态、签名版本清单、安装包及受限诊断接收；新增反馈端点须完成下述部署后才可用。测试阶段使用固定 IP SAN 证书，客户端只信任随程序附带的公钥证书，未关闭 TLS 校验。接收接口采用格式、大小、速率和并发限制；当前没有客户账户身份认证，因此匿名上报或反馈不能作为可信计费或授权依据。

## 新增反馈端点与部署合同

| 端点 | 访问范围与行为 |
|---|---|
| `POST /v1/feedback` | 公网 HTTPS；接收固定反馈 ID、正文、分类、客户端信息、可选诊断及回执凭据。相同 ID/内容/凭据返回同一记录的当前回执，内容或凭据冲突返回 409 |
| `POST /v1/feedback/status` | 公网 HTTPS；一次查询 1～100 个 ID，每个必须携带对应回执凭据。任一缺失或不匹配返回 403；不提供公开列表 |
| `GET /api/feedback?offset=0` | 仅回环管理后台；每页最多 100 条，返回正文、处理状态和仍在保留期内的脱敏诊断，不返回回执凭据 |
| `POST /api/feedback/status` | 仅回环管理后台，校验本机 Host 和同源 Origin；按 ID 更新 `pending`、`in_progress`、`resolved`，连续不同状态更新时间严格递增 |

JSON 请求上限 64 KiB；当前全局每分钟 300 次、单地址每分钟 60 次限制与既有接收接口共用。客户端正文和后台内容按普通文本显示。服务端只保存回执凭据的 SHA-256 摘要；反馈诊断 30 天到期清理，正文、状态、内容摘要与凭据摘要保留，以便继续查看和幂等重试。备份包含反馈正文，按用户反馈数据管理。

部署时需将 `service.py`、**`feedback.py`**、`admin.html`、`promote.py` 和 `install.sh` 作为同一版本复制。`service.py` 现在直接导入 `feedback.py`，只更新主脚本会导致启动失败；`install.sh` 已包含该模块的安装。既有服务器应先备份 SQLite，再替换同版本程序文件并重启 `ai-maintenance`；启动会在原库中创建反馈表及索引，保留旧诊断、issues 和发布文件。初次部署沿用 `install.sh <server-ip>`，不新增公网后台端口。

既有服务更新使用同提交的 `upgrade.sh`：将它与上述服务文件放到同一个上传目录，执行 `sudo sh <上传目录>/upgrade.sh`。脚本先校验 Python 源码、使用 SQLite backup API 备份数据库并保留旧代码，再停止服务、替换文件并检查回环管理接口；失败恢复旧代码。不会重签 TLS 证书、改客户端信任或替换已发布安装包。备份保留在 `/var/lib/ai-maintenance/backups/`，本身包含反馈数据，不作为公开下载内容。

本次已通过本地临时数据库和回环 HTTP 的幂等、错误凭据、公开端拒绝列表、后台权限、状态更新和诊断到期保留正文检查。实际服务器部署后仍需检查进程健康，并用明确的测试反馈完成“客户端提交 → 后台改状态 → 客户端刷新”闭环；此处仅记录部署步骤，本轮未执行部署。

## 发布测试更新

1. 依据项目 README 从干净且已确认的提交生成**完整测试安装包**及对应 manifest。编译不等于完成安装包验证。
2. 在 `desktop/` 运行 `node scripts/publish-cloud-release.cjs <installer.exe> <manifest.json> [notes.txt]`。脚本校验测试 appId、版本、包大小及 SHA-256，使用本机 `.ssh/ai-release-signing.pem` 签名，通过 SSH 上传。
3. 服务端核验包摘要，原子切换频道版本，保留历史签名清单。版本与序号必须递增。客户端校验 Ed25519 签名、频道、appId、平台、版本、序号及安装包哈希，安装前再次核验。
4. 回退代码时发布一个更高版本号的修复包，不降低版本指针。签名私钥不得上传服务器、入库或打包。离线保管签名与 SSH 私钥的备份；丢失签名私钥后需要可信的新安装包迁移，不能假设旧客户端会自动接受新密钥。

`build-cloud-smoke.cjs` 和 `--smoke` 专用于隔离机制验证，appId、安装目录及数据目录独立，不是完整产品发行包。它会发送明确构造的测试错误，自动更新后退出；不能分发给客户。

## 服务维护

源码：`service.py`、`feedback.py`、`admin.html`、`promote.py`；`install.sh` 用于服务器初次部署。服务名 `ai-maintenance`，程序目录 `/opt/ai-maintenance`，数据目录 `/var/lib/ai-maintenance`，TLS 证书 `/etc/ai-maintenance`。使用无登录服务用户及 systemd 隔离，内存上限 384 MB。

通过已有 SSH 连接执行 `sudo systemctl status ai-maintenance` 查看状态；后台证据也可从回环 `/api/overview` 读取。备份 SQLite 应使用 SQLite backup API 或停服务后复制数据库，避免遗漏 WAL。同时保存 releases 和 artifacts；不要只备份 latest 指针。旧包、上传暂存目录及本机更新缓存目前不自动删除，按项目清理规则确认候选后处理，注意服务器磁盘用量。

后续正式启用：准备域名及适用的备案、有效 HTTPS 证书，配置正式频道与安装目录，在本机完整版本验收基础上补齐目标电脑、实际任务退出及人工功能验收，再发布。修改 IP 或证书会影响旧测试客户端连通，应在旧连接仍可用时先发布迁移版本。
