## 证据与原因

用户提供的 1.2.10-test 诊断包来自微信 4.1.15.13。前两位联系人约耗时 4 分 51 秒；文字均有发送成功回执，图片均出现三次 `image_draft_format_unavailable`，记录的发送动作未执行。重复定位、核验、恢复退避占据主要时间；等待原因在工作流控制器中丢失，界面误呈现为笼统等待。用户已确认同机同图手动复制、粘贴、发送正常。

源码发现并修正的实际问题：图片操作未沿用文字已验证的输入落点；粘贴位图后立即写文字哨兵可能与微信读取剪贴板竞争；原计时公式重复累加小数秒，跨秒时可能回退；整体预算耗尽仍合成第二次超时，覆盖可信的未点击证据。这些是程序链路缺陷，但旧诊断缺少落点和剪贴板序号等证据，仍不足以断言故障机的唯一触发点，不能归因于电脑性能下降。

## 实现

- 共享输入落点解析，沿文字回执的会话锚点传递到图片；继续校验当前窗口、会话和输入框。图片读回保留刚粘贴的位图，仅复制导致剪贴板序号变化后读取，并核对尺寸和像素指纹。
- PowerShell 使用 `Stopwatch.ElapsedMilliseconds`；JS 总预算使用单调时钟。预算不足不启动或虚记重试，可信的发送前失败保存 `not_attempted`。点击阶段另行锁存，不受最近 40 条进度裁剪影响；点击后或证据不足维持 `outcome_unknown`，不自动补发。
- 图片读回的有界恢复耗尽且确认未点击后，上层直接复用失败记录及连续失败停止规则，不再叠加整联系人恢复；已发文字回执保留。
- 现有工作流更新通道传递联系人序号、消息部分、阶段、读回恢复次数、发送前恢复次数及倒计时。主页面和浮窗共用展示逻辑；恢复等待与定时执行分开，部分发送明确显示。上一轮延迟回调不能覆盖下一轮。
- 联系人间隔统一为 **5 秒**，旧任务已经落盘的等待自然结束；不更改用户操作避让、身份核验或未知结果停止规则。5 秒不代表单个联系人的总处理耗时。
- 诊断只增加枚举、数字和布尔字段，包括落点来源、序号是否变化、格式类别、阶段及核验失败类别；不增加剪贴板正文记录。旧日志 `details: null` 继续兼容。
- 登录页左上角完整显示用户提供的 640×640 JPG，默认 64×64 CSS 像素。源文件与 `desktop/public/xilianhui-logo.jpg` SHA256 相同：`DAC5A472E7E7D6152653B5AD666B4A56E3D4FF366613370EE6D4C8A24801FE64`。
- 内容区共用一个“返回…”入口，复用导航父级。短视频、微信、精准获客的功能页回模块首页，模块首页回主页面；混剪素材及制作记录先回混剪。移除重复返回及废弃样式，返回不暂停后台任务。
- 短视频首页左侧介绍和功能、右侧两个原有成片示例，封面下展示模块、时长、标题和播放入口；小窗口上下排布。保留原播放器及产品详情图页面。
