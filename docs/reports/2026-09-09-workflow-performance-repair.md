## 因果链与更优解

### 1. 自动回复拖住计划任务：调度规则导致饥饿

旧调度器每轮先调用自动回复，返回 `handled` 或 `busy` 就退出，根本没有机会选取后面的待办。持续有消息或扫描持续忙碌时，有限任务一直等不到执行。旧回归还明确断言“回复优先”，说明这是旧产品规则而非随机并发故障。

按本次反馈改为：**当前可执行的有限任务优先；队列空闲时自动接待。** 未来预约任务不阻止空闲接待，已经开始的一次回复不强行中断。触达、发布和互动仍由同一调度器串行执行，各模块继续独立核验目标窗口；不通过放松会话识别获得速度。

实现：[wechat-workflow.cjs](../../desktop/src/main/wechat-workflow.cjs)。界面说明同步修改；原有暂停、账号隔离、每日任务、失败记录和未知结果禁止自动重发的规则保留。

### 2. 朋友圈观察超时：计算成本和重复探测叠加

现场持续诊断确认该次操作确实发生在 1.1.6：互动任务总耗时 87,503 ms，其中观察命令 45,063 ms 后被外层终止。前一条发布任务耗时 55,797 ms，记录为 `moments_open / powershell_timeout / failed_before_action`。用户描述已经发表，但这条发布记录不能证明实际发表结果，不能据此自动重发。

集成式朋友圈直接使用视觉探测；旧代码在视觉探测超时后又落入通用回退，再执行同一个最长 30 秒的探测。两个内层预算可能超过外层 45 秒，外层终止还会丢掉更具体的内层原因。现已禁止集成式窗口重复走相同探测；独立窗口仍保留结构识别失败后转视觉识别的有效回退。

图像扫描需要在同一张冻结图片上检查大量头像候选。旧版由 PowerShell 反复解释每个候选的像素循环；现在只把这段纯计算放入已有 C# 类型，使用同一采样间隔、颜色阈值、边框隔离规则和打分，仍保留两帧帖子稳定性验证。合成图的新旧候选完全一致，扫描从 **4,860 ms 降至 437 ms**；这只代表本机该环节，不能换算为异机整条任务的加速比例。

实现：[moments_dry_run.dev.cjs](../../desktop/rpa/active_touch/moments_dry_run.dev.cjs)、[moments_visual_probe.dev.cjs](../../desktop/rpa/active_touch/moments_visual_probe.dev.cjs)。

### 3. 启动和窗口枚举成本仍需异机复验

测试机一位客户的触达总耗时 182,220 ms；窗口准备约 11～12 秒，其中进入窗口脚本前的进程启动及公共初始化约 7.8 秒。不能把这段时间全归给微信响应，也没有证据证明是杀毒、权限或 CPU 的某一个原因。

朋友圈导航旧实现对每个桌面窗口反复调用 `Get-Process`。已改为一次获得微信 PID 集合，再枚举并过滤窗口；仍在每次枚举前更新集合，保留窗口归属校验，不跨操作缓存未经复核的窗口句柄。

补齐导航、截图、页面证明、候选扫描等固定技术阶段及总耗时，超时时只提取固定标记，不上传 stderr、聊天文字或截图。客户端、观察结果、发布失败日志和服务端白名单同步支持。服务端修改仅完成本地 HTTP 验证，尚未部署。

**尚未解决的范围：** 测试机约 7.8 秒的冷启动/公共初始化仍未证明消除，原机导航超时的具体内部慢阶段也缺旧日志证据。后续如仍慢，应根据新阶段日志定位；复用进程需同时设计退出、取消、窗口重新校验和异常隔离，不能简单让旧工作进程长期存活或提高所有超时。
