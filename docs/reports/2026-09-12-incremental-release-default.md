# 内部更新统一优先增量

## 本次范围

用户要求统一日常更新方式。发布工具和仓库约定已改为默认组件增量，完整安装器使用显式 `--full`。本次不重建、不替换已发布的1.1.20，不调整服务器频道；下一次发布须按约定递增版本并验收。

## 核实的问题

- 当时公开整包频道为1.1.20、527349620字节，增量频道仍为1.1.17。客户端本来就会在版本相同且底座兼容时优先组件，因此只发布新版整包会让用户继续下载整包。
- `README.md` 和默认 `release:internal` 命令指向整包，而内部标准又要求兼容业务更新走增量，入口不一致。
- 原1.1.19安装目录备份与1.1.20完整目录均有3542个基础文件；只有 `resources/content-engine/_internal/base_library.zip` 不同。两个ZIP都含155个文件，逐文件内容和元信息一致，区别仅为排列顺序；原摘要检查因此要求完整升级。
- 原增量构建虽然验证了组合目录，却在返回前删除该目录，与文档承诺的保留候选不一致。

## 实现

- `release:internal` 默认构建组件，`publish:internal` 默认读取本地组件清单。`--full` 才选择完整安装器；原组件命令共用同一构建入口。没有把普通构建失败自动转换为整包。
- 默认参考上次完整候选目录；`--base` 可指定已经验收的安装目录。构建后核对基础文件摘要、底座版本和数据模式，不兼容时给出实际文件差异，不发布无法使用的增量。
- 内容引擎和产品详情图共用Python库处理：验证参考文件与基础清单的SHA-256一致，逐项比较ZIP文件名和解压后内容；完全相同时沿用已验收ZIP字节，内容确有变化则保存新依赖并稳定排列。只写本次新构建目录，已验收文件不变。处理发生在运行时自检和清单生成之前，运行时缓存指纹包含处理脚本与参考摘要。
- 已通过组合检查的增量候选保留在 `release/components/test/candidate-*`，路径记入构建记录和组件验证记录的 `candidateRoot`，供本机实际更新验收。旧完整安装器不受影响。
- 同步当前仓库 `AGENTS.md`、`README.md` 和内部更新标准，避免后续任务因读取不同入口而选择不同发布方式。

- 真实归档回放通过：把1.1.19的归档作为下一次随机排列的构建输入，对照1.1.20已验收底座后，155个文件均保持一致，归档摘要变为已验收的 `12902f7667ab58e9d61aa4f5c74a947c83c3b978e2b97f1b473b147c5fcef260`；整个基础文件指纹恢复为 `8aeab74252cc4ba1258ffa46c0112429511eab3483e6595208065c25a21f7e9b`。原安装包和参考文件未修改。
- 语法检查和完整 `npm.cmd run check:self` 通过，包含更新协议、组件组合、两个Python运行时、缓存、安装器及版本边界检查。本次没有执行新的完整构建、真实增量切换或云端发布，不能把离线回放当成新版本安装验收。

## 使用与回滚

日常：`npm.cmd run release:internal` → 本机验证候选与实际切换 → `npm.cmd run publish:internal`。首次安装、已确认基础环境改变或明确要求离线包时，使用同一入口的 `--full`。原1.1.20用户无需为本次工具调整重新安装。

当前机制是组件增量，并非逐文件二进制差分：改变某组件时会下载该组件归档，未变组件复用。不能承诺每次更新都只有几KB，也不能让首次安装完全省去基础环境。

本次仅改发布工具与文档。若新工具实际构建出现异常，保留失败记录并修正对应步骤；已发布的1.1.20及原回滚副本不变，不通过放宽签名、摘要或版本检查来强行升级。回滚本次工具提交不会改变安装中的应用或云端版本。

原始回放及检查日志位于本地 `outputs/incremental-default-20260912/`；日常执行标准见 [内部更新标准](../internal-release.md)。
