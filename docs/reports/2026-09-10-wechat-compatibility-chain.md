# 微信兼容链路修复：第一次流程试跑

## 现场与范围

基线为干净工作区 `10b6bcf`。故障反馈来自 Windows 10 19045，安装版 `1.1.10 / 20260909T1347Z`，2026-09-10 09:22。

- 精准触达 `prepare_window` 成功，主窗口数量 1，旧渲染子窗口数量 0；随后 `click-search-result-dry-run` 失败，发送未尝试。
- 朋友圈发布与互动分别报 `moments_render_pane_not_found`，发布动作前停止，互动完成数 0。
- 本轮反馈没有自动回复的新失败日志，不能把三条任务日志误写成三个业务模块都已确认同一根因。

原始技术反馈及本轮工具位于忽略目录 `outputs/wechat-failure-20260910/`，没有回复、公开或关闭服务端反馈。

## 失效假设与同类排查

1. **视觉路径必须有 UIA 渲染控件。** 现场已有可见窗口但 UIA 空树。上轮仅修主窗口识别，朋友圈导航、观察、滚动及动作前验证仍依赖相同旧控件。导航还重复定义同名 resolver，可能覆盖共享实现。
2. **无法识别的驱动错误就是找不到窗口。** 触达状态机把剪贴板无法保留、脚本返回无效等错误统一映射到 `wechat_window_not_found`。这是已确认的信息丢失缺陷，但不能反推本次触达一定由剪贴板导致。

检查范围覆盖共享窗口准备、联系人搜索/会话校验、自动回复视觉驱动，以及朋友圈进入、观察、动作、滚动、发布与返回路径。自动回复已有视觉路径不强制依赖该 UIA pane，本轮不无证据重写。

## 本地修改

- 抽出 `wechat_render_surface.cjs`。旧 UIA pane 继续优先；仅根控件确为同进程顶层窗口、子控件为零时，读取真实 Win32 客户区。部分可读但不匹配、歧义、越界和身份冲突仍拒绝，不以缺少证据等同成功。
- 新来源明确标记 `visual_win32_client / Win32ClientSurface / Win32.Client`，身份包含进程、窗口句柄和进程启动代际；不伪造 UIA 名称或 runtimeId。共享 JS 验证替代三处重复条件，观察、保存、动作锁和滚动同步适配，renderer 返回类型同步。
- 导航移除重复 resolver；窗口范围复验、发布入口均复用同一来源。客户区只是边界，仍需朋友圈页面视觉证据、帖子稳定性、前景与点归属、输入租约和结果确认。
- 触达保留已知具体错误，未知错误报告 `wechat_operation_failed`，不复制任意原始错误文本到日志。搜索驱动真实无窗口分支明确返回对应错误。
- 现有只读工具升级 v3：复用生产观察函数检查客户区、当前朋友圈页面和相机；剪贴板只记录格式类别，控件名称仅保留导航白名单。输出本地 JSON，无点击、输入、发布或上传，启动后等待 6 秒供用户切回微信。

## 验证证据

- 测试界面构建通过；主动触达、窗口布局/候选选择、朋友圈导航、发布驱动、动作以及自动回复视觉驱动的现有隔离检查通过。
- 新模式通过观察→保存→动作校验的回归；换成其他 HWND 的身份被拒绝。
- 临时屏幕外原生窗口实际验证：空树返回 Win32 客户区；旧 pane 保持 UIA 路径；错误 PID 与部分不匹配控件树被拒绝。未操作真实微信。
- 视觉大检查执行到最后的新增 native 夹具时，因 Add-Type 无公共成员警告混入 stdout 导致 JSON 解析失败；修正夹具的已知警告输出后，native 夹具独立通过。此前业务断言已通过，没有把最初失败的整次进程写成全量通过。
- 新共享模块在测试与交付版打包来源过滤中均被包含。没有生成或安装新应用包。
- v3 工具本机生成与执行通过，本机无微信进程，输出 `windows: []`；这不证明故障机相机或任务通过。

用户返回 `wechat-compatibility-20260910-094954.json` 和 `wechat-compatibility-20260910-095028.json`。两份均为 schema 3，Windows 10 19045，微信实际版本为 **4.1.13.65**，不同于项目原验收目标 4.1.11.55。
