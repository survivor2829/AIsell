# 精准触达全链路调查单：身份不唯一跳过 / 跳过记录刷屏 / 门禁盘点

- 日期：2026-09-17
- 性质：只读调查报告（审查方产出），供 Codex 核实后出回应单
- 用户反馈的三个问题：
  1. 明明搜得到联系人、看起来可以点进聊天窗口，程序却不点，悬浮窗显示"已安排执行时间"，几秒后跳到下一个（大量出现）；
  2. 每次跳过都逐条显示在"精准触达"界面，上百条排上去观感差；且手动重试也没用，还是老样子；
  3. 想知道精准触达全链路一共有多少门禁，是否有可以拆掉的"枷锁"；同时要求版本迭代不得破坏既有功能。

---

## 一、问题 1：为什么"看得见却不点"

### 1.1 点击授权机制（wechat_search_result_resolver.cjs）

程序点击搜索结果前，不采用"名字看起来像"这种软判断，而是要求**硬证据**，按优先级依次尝试 6 条授权路径：

| 路径 | mode | 要求 |
|---|---|---|
| 1 | unique_local_uia | UIA 树唯一候选且身份匹配 |
| 2 | identity_matched_uia | UIA 多候选中恰好一个匹配 |
| 3 | exact_wechat_id_visual | OCR 读到「微信号：xxx」且与目标精确一致 |
| 4 | unique_local_visual | OCR 读到「微信号：xxx」标签且唯一 |
| 5 | exact_wechat_id_local_visual | 无标签但文本精确等于查询且结构佐证唯一 |
| 6 | unique_local_surface_visual | 名字+紧凑表面结构唯一佐证 |

全部路径失败时按规则拒绝（search-r001/r007/r008/r013/r014/r015 等），reason 统一为 `search_result_identity_unverified`。

**关键结论**：人眼看到"张三"觉得肯定是他，但程序要求 OCR 把「微信号：」标签读出来并匹配。微信搜索下拉列表在连续作业时 OCR/渲染慢一拍，标签读不全 → 无硬证据 → 拒绝点击。这不是 bug，是 1.1.43 修复"误点网络查找"后刻意收紧的授权设计——收紧方向正确，但**恢复等待没有跟上**。

### 1.2 重试为什么没用（touch-workflow.cjs:385-400）

- 身份核验失败后自动恢复：`IDENTITY_RECOVERY_ATTEMPTS = 2`，间隔 `attempt * 2_000ms`，即 **2 秒、4 秒**。
- 2 秒后微信下拉列表大概率还是同样的渲染状态 → 第二次同样失败 → `identity_skipped` + 拉黑该候选。
- 本机 2026-09-15 实测数据（run_logs.jsonl）：失败轮等待仅 2-4 秒，**成功发生在等待 15-20 秒之后**。重试间隔远短于微信渲染恢复所需时间，所以"重试也没用"。
- 悬浮窗"已安排执行时间"：重试以 `pending + retryAfterMs` 调度返回，UI 显示为等待状态。用户看到的就是这 2-4 秒等待窗口，等完仍失败即跳下一位。

### 1.3 待核实项（需 Codex 用客户机日志确认）

用户说"跳过上百个"。本机无客户机日志，需确认：跳过率（跳过数/总联系人数）、集中的 rule_id 分布、是否与跑量时长正相关（连续作业越久 OCR 环境越差）。

## 二、问题 2：跳过记录刷屏

### 2.1 现状（App.tsx:1409-1464）

- `touchTask.skipped_records` 逐条渲染在 `floating-skipped` 面板：`本次跳过 N 位` + 每位一行。
- 数据源已有 `skipped_breakdown`（identity / ai_failed / outcome_unknown 计数）字段，但列表仍逐条平铺。
- 每条身份类跳过附"重试"按钮（retrySkipped），但手动重试走的是同一套快速链路——底层等待不足的问题不修，重试必然复现失败，与用户观察一致。

### 2.2 改进方向

- 默认汇总显示（"本次跳过 N 位：身份不唯一 X、AI 失败 Y、结果未知 Z"），明细折叠点开。
- 手动重试必须复用 D1 的新等待策略，否则按钮形同虚设。

## 三、问题 3：门禁盘点（全链路）

### 3.1 三层结构（这是理解"407 条是不是太多"的关键）

| 层 | 数量 | 实际作用 |
|---|---|---|
| 规则目录 wechat-rule-catalog.json | **407 条** | **诊断编号登记簿**，不是 407 道运行时拦截。运行时只做两件事：失败时按 ID 查分级、打包自检确保每个 throw 字面量都登记 |
| 失败策略表 wechat-failure-policy.cjs workflowPolicies | **22 条** | **真正的决策表**：决定等待/跳过/停机。blocker 14、environment 5、recoverable 3；其中 attentionScope=global（整单停机）15 条 |
| 打包自检门禁（self_check） | 若干 | TickCount64 黑名单、throw 字面量完整性等，只在构建期运行 |

### 3.2 规则目录 407 条的真实分布

| 所属模块 | 条数 | 占比 |
|---|---|---|
| 朋友圈发布（moments_publish / visual_action / navigation） | 275 | 67.6% |
| 窗口驱动（wechat_window_driver 两文件） | 89 | 21.9% |
| 图片发送（wechat_image_send） | 27 | 6.6% |
| **搜索结果解析（精准触达点击授权）** | **15** | 3.7% |
| 触达工作流 | 1 | 0.2% |

**结论：用户感知的"门禁过多"主要是朋友圈模块的登记数量造成的观感；精准触达链路真正的决策门禁只有 22 条策略 + 15 条搜索授权规则 + 27 条图片规则。** 规则数量本身运行时开销≈0，不构成枷锁。

### 3.3 真正构成"枷锁"的是这三处（不是数量）

1. **身份恢复重试间隔过短**（2s/4s）——本报告问题 1 的直接根因；
2. **策略表 15 条 global 停机**——部分 reason 是否需要整单停机值得逐条复核（如某些 environment 类可降为 task 级），但 1.1.42 Tier1 已做过一轮分级治理，剩余条目需逐条给证据，不能一刀切；
3. **UI 逐条刷屏**——观感问题，非运行时枷锁。

### 3.4 不能拆的门禁（底线，明确列出防误伤）

- 发送前草稿确认（防止空消息/误发）；
- `outcome_unknown` 不自动补发、结果不明保持暂停——这是防重复打扰客户的底线；
- 1.1.43"网络查找整行"黑名单——防误点搜索页的"搜索网络结果"；
- 打包期自检门禁（TickCount64 黑名单、throw 字面量完整性）——这些正是"版本迭代不破坏旧功能"的保障，拆掉它们才会让老功能坏掉。

## 四、修复指令（D 系列，供 Codex 核实后回应）

用户已明确选择：**只加等待，不放松点击授权**（不增加误发风险优先）。

- **D1**：身份自动恢复重试间隔从 2s/4s 改为递增 **2s / 8s / 20s**，`IDENTITY_RECOVERY_ATTEMPTS` 由 2 提至 3。等待仅作用于已失败的联系人，不影响正常联系人的节奏。依据：9-15 本机实测 15-20 秒等待后识别成功。
- **D2**：`floating-skipped` 面板默认汇总显示（用现成 `skipped_breakdown` 计数），明细列表折叠、点击展开；不改 `skipped_records` 数据结构，纯展示层改动。
- **D3**：手动"重试"按钮（retrySkipped）复用 D1 的等待策略；重试若再次失败，保留跳过且说明原因——不允许重试走比自动恢复更差的路径。
- **D4**（评估项，本轮只评估不改码）：Codex 逐条列出策略表 15 条 global 停机 reason，给出"维持 / 可降为 task 级"建议及依据；涉及发送安全的一律建议维持。
- **D5**（防破坏回归）：D1-D3 改动后，本机 harness 回归验证——正常联系人全流程不受影响、失败联系人的等待节奏符合新配置、跳过面板汇总正确。通过前不打包。

## 五、验证边界

- "上百个跳过"的具体分布与跳过率待客户机日志核实（见 1.3），若 D1 实施后客户机跳过率仍显著，需回看 rule_id 分布再议（包括是否启用重试降级授权——用户本轮未授权，未列入指令）。
- 本报告不改动任何代码；D4 为评估项，不随 D1-D3 混提交。
