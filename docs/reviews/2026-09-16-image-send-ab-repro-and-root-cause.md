## 1. 一句话结论

**新版图片脚本存在已被本机 A/B 实验实锤的代码回归：它把"输入租约检查"塞进了注入按键后的亚百毫秒轮询环，导致脚本自己的键盘注入被误判为"用户外部输入"（`wechat_external_input_detected`），图片发送在 read_back 阶段必然失败。** 旧版脚本（6a8f1cb，09-09）在同一台机器、同一个微信窗口、同一张图上 2/2 成功；新版 2/2 失败。这与"之前可行、改着改着不可行"完全吻合。

## 4. 机制证明：输入租约的"自身输入尾部"竞态

微实验（Temp/tick-race.cjs，两次运行结果一致）：

```
tick_before=27860062 tick_after_sendwait=27860125 tick_60ms_later=27860203
refresh_captured_own_input=True
tick_changed_after_refresh=True     ← 关键：刷新后 60ms，系统输入计时又变了
```

机制链条：

1. `Image-Keys` 调 `[System.Windows.Forms.SendKeys]::SendWait("^c")` 后**立即**刷新 `$script:inputTick`；
2. 但注入的按键序列（Ctrl down / C down / C up / Ctrl up）的**尾部事件在 SendWait 返回之后才被系统输入队列处理**，`GetLastInputInfo` 在刷新之后继续变化（实测 +78 ticks）；
3. **旧版**：^c 之后固定 `Start-Sleep 120ms` 才做一次 `Assert-ImageWindow`——尾部（约 80ms 内）已落地，侥幸通过；
4. **新版**（b774489/e7d4671 引入）：
   - `Read-ImageDraft` 的剪贴板序列号轮询环内**每 40ms 调一次 `Assert-ImageWindow`**（内含租约检查）；
   - 粘贴后、`Image-DialogEvidence` 等新增检查点也紧贴注入动作；
   - 40ms < 注入尾部时长 → **租约检查必然撞上自己的输入尾部** → 误报 `wechat_external_input_detected` → 抛异常 → 发图失败。

**这不是环境问题，是纯代码回归。** 客户机上同类误报（image-r005/r010、外部输入类失败）同理解释：客户机更慢、注入尾部更长，撞线位置更多。

## 7. 给 Codex 的修复指令（先回应单，确认后再动代码）

### X1（根修）：输入租约必须"沉降"而非"瞬时刷新"

现状：每次自身注入后单点刷新 `inputTick`，尾部事件落在刷新之后。

要求：自身注入（SendKeys/SetCursorPos/mouse_event）之后，不再做单点刷新，改为**沉降循环**：连续读到 `GetLastInputInfo` 值稳定（如 2 次间隔 30ms 读数相同）或 250ms 超时后，才把 `inputTick` 更新为稳定值；或将"自身注入后 250ms 内的 tick 变化"定义为豁免窗口，不计为外部输入。两方案选一或并用，覆盖 `Image-Keys`、`Click-ImagePoint` 的 SetCursorPos+mouse_event 尾部。

### X2：把租约检查移出亚百毫秒轮询环

`Read-ImageDraft` 剪贴板序列号轮询环（40ms 一圈）内的 `Assert-ImageWindow` 只保留窗口身份检查（可见性/PID），**租约检查移出轮询环**，在环结束、进入下一阶段前执行一次（配合 X1 的沉降）。

### X3：客户机两类挂起的可观测性加固

- X3-a：合成脚本最顶部（Add-Type 之前）打一条 `image_send_stage:script_started` 标记 + 组合脚本各预加载段（DPI 引导 / 取证脚本 / 观察脚本 / 图片 Add-Type）各自的耗时 stderr 行——1.1.44 零标记挂起再现时可直接定位卡在哪一段；
- X3-b：SetText/SetImage 前增加剪贴板可写探测（短超时 Open/Close 探针）；现有 5 次重试只覆盖 0x800401D0 异常，对"被长期锁死不抛异常"无效——把剪贴板写放入子 STA 线程 + Join(timeout) 兜底；
- X3-c：粘贴后（当前固定 350ms）改为轮询等待剪贴板序列号/前台稳定后再继续，避免微信仍在读大位图时脚本抢写哨兵。

### X4：验收协议

## 8. 补充验证（结论复核后的代码级精修）

应"你确定哈"的复核要求，对两版脚本做了逐行对照。结论不变，机制表述精修如下：

**两版的租约原语完全相同**（`Assert-ImageLease` 比较 `GetLastInputInfo` 与刷新值，`Assert-ImageWindow` 开头必查租约）——旧版脚本行 250–259，新版 301–310，一字不差。**回归不在"有没有检查"，而在"检查密度与位置"**：

| 脆弱窗口（自身注入后） | 旧版 6a8f1cb | 新版 HEAD |
|---|---|---|
| ^c 之后（read_back） | 固定睡 120ms，**查 1 次**（脚本行 306–308） | 40ms do-while 轮询，**每圈都查**（392–396 行 `Assert-ImageWindow`→租约），最长 120+80×n ms |
| 剪贴板忙重试间隔 | 无租约检查 | 每次重试后查（295–296） |
| 图片重试环（expectImage） | 不存在 | 每轮 ^a 前查（405–406） |
| ^v 粘贴后 | 350ms 后查 1 次（389–390） | 350ms 后查 1 次（499–500，同旧版） |
| 发送点击确认环 | 200ms 环内查（424–426） | 同构（539–540） |

**诚实修正**：第 4 节第 3 点"旧版侥幸通过"应理解为**概率性幸存**——旧版 120ms 的单次检查理论上也能撞上注入尾部，但它每次发送只暴露 1 次；新版在同一窗口内暴露 3–5 次以上且首轮就在 40ms 处（实测尾部落地约 +78ms），暴露频率高一个数量级，**从"可能撞"变成"必然撞"**。这与 A/B 结果（失败点固定、耗时 145s→27s 漂移）完全吻合：固定失败点 = 轮询首轮必查，耗时漂移 = 前置阶段（剪贴板忙重试等）的概率路径。

**对修复指令的影响：无。** X1（沉降）+ X2（租约移出轮询环）正是针对"检查密度×注入尾部"的结构性解法，两个方案都能同时消除旧版的概率隐患和新版的必然撞线。请 Codex 实施时以 errorLine 实际映射核实首轮抛出点（审查方按脚本字符串行号定位到 read_back 轮询环，与 stderr stage 标记一致，但最终以你们的行号映射为准）。
