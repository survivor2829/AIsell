## 2. 误点问题的根因（置信度：高，代码证据充分）

### 直接原因

提交 `00a7876`（09-14 17:15，"treat unlabelled local exact-id result as selected"）给 `wechat_search_result_resolver.cjs` 新增了一条认定路径：

```
exact_wechat_id_local_visual：当没有任何带"微信号:"标注的联系人候选时，
若存在一条文本恰好等于搜索 ID、未被 composesNetworkEcho 配对进网络区、
且位于"搜索网络结果"分隔线上方 max(72px, 3倍行高) 内的候选 → 直接当作选中并点击
```

**问题**：微信搜索弹窗"更多"分组里的"网络查找微信号： huatengcangku"行，其数值文本就是精确的搜索 ID。当 OCR/UIA 把该行的"网络查找微信号:"前缀与 ID 值拆成两个元素（或前缀元素没被采集为候选）时：

- `composesNetworkEcho` 无法把 ID 值与前缀配对（前缀不在候选里）；
- 该行位于"搜索网络结果"分隔线上方 → 通过 `isNearbyLocalResult`；
- 弹窗内没有带标注的联系人候选（"崔总 华腾仓库扫地车…"昵称行无 "微信号:" 标注，或未被采集）→ `labelledCandidates.length === 0`；

三个条件全部满足 → **网络查找行被当作联系人点击** → 打开"查找微信用户"资料弹窗（截图 2）→ 下游会话核验失败 → 重试 → 再点 → **死循环**。

### 为什么"以前没有、最近三个版本才有"

- `00a7876` 于 09-14 提交，此后构建的 1.1.40 / 1.1.41 / 1.1.42 全部包含它——与"连续三个版本都出现"的时间线完全吻合。
- 09-14 之前，精确 ID 搜索若无带标注候选 → 一律 reject（`search_result_identity_unverified`），**宁可不点也不点错**。这个老行为"卡"但不"错"。`00a7876` 的本意是修"微信把本地结果渲染成无标注行导致永远点不到"的问题，方向没错，但**没有把"网络查找微信号"回显行从候选里结构性排除**。

### 日志佐证（客户机 failure-evidence）

- 09-15T13:17Z 起 `search-r008` ×6、`search-r014` ×10（14:13–14:16Z，间隔约 11 秒）——正是"点了 → 弹窗 → 核验失败 → 重试"的循环形态。r014 连续 10 次说明**同联系人身份失败的重试上限过宽（约 10 次），循环breakers缺失**。

## 3. 修复指令（给 Codex，一次改到位）

### F1（核心）：把"网络查找微信号"行从可点击候选中结构性排除

- 在 `resolveWechatSearchResultObservation` 入口处显式识别网络查找行：凡文本匹配 `^网络查找微信号` 的元素，或与该元素同行（垂直重叠）/同一视觉行的候选，**一律不得进入 `exactUnlabelledLocalCandidates` 与 `uniqueCompactLocalSurface`**。
- 不要依赖 `composesNetworkEcho` 的几何配对来"碰巧"排除它——配对失败正是本次事故的触发条件。结构性黑名单优先于几何启发式。
- 保留 `00a7876` 想修的原问题（真正的无标注本地联系人行）：可与"网络查找"行做**行级区分**——本地联系人行带头像占位与昵称文本，网络查找行带绿色人形图标与"网络查找微信号"前缀。若无法可靠区分，宁可回退为 reject（老行为，卡而不错）。

### F2（防循环）：点击后必须验证落点表面，错了必须止损

- 点击候选后，若打开的是"查找微信用户/添加朋友"资料弹窗而非聊天/联系人会话表面 → 判定误点：`Esc` 关闭弹窗、**将该候选标记为 poisoned（本次任务内永不再点）**、该联系人按"身份未确认"进入未触达名单。
- 同一联系人同一失败规则连续 ≥3 次 → 强制跳过该联系人（昨日 r014 循环 10 次说明现上限太宽）。
