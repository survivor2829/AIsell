# 全局交叉审查报告：精准触达为何修不完

> 审查日期：2026-09-15 ｜ 审查视角：旁观者 / 产品经理 / 高级工程师
> 范围：全项目方向 + 精准触达（active_touch）根因
> 性质：只读审查，未修改任何代码，未运行测试

---

## 一、总判断

**精准触达的问题不是"bug 太多修不完"，而是修复模式在数学上不可能收敛。**

从 1.1.21 到 1.1.27（09-12 至 09-14，三天 7 个版本），所有修复都在做同一件事：**给身份核验器加启发式分支**。但分支空间由微信客户端在不同机器上的渲染行为决定——这是不可枚举的。本机（Win11 + 微信 4.1.13.65 + UIA 正常）测得再绿，对故障机（Win10 19042/19045 + UIA 空控件树 + OCR 拆词 + 慢）没有预测力。

一句话：**在错误的方向上，执行得越好，版本号涨得越快，问题离解决越远。**

## 三、四个根因（附代码证据）

### 根因 1（代码层）：身份核验是"枚举好形态"策略，而目标形态不可枚举

`desktop/rpa/active_touch/wechat_search_result_resolver.cjs`（268 行）：

- 通过模式 6 种：`unique_local_uia` / `identity_matched_uia` / `exact_wechat_id_visual` / `unique_local_visual` / `exact_wechat_id_local_visual` / `unique_local_surface_visual`（:263-264）
- 返回 `unverified` 的路径 10+ 条（:208, :218, :223, :229, :257-258……），**默认答案 = 拒绝**
- 1.1.25 加的 OCR 片段几何重组（`labelledWechatIdCandidates` :83-116）是典型枚举式补丁：今天覆盖"CB+1668 拆两段"，明天 OCR 引擎换个版本拆成"C+B1668"就再次失效

**枚举式防线的覆盖率上限，由对手（微信渲染管线）的变化速度决定。这是打地鼠的数学本质。**

### 根因 2（环境层）：本机与故障机是两个世界，测试夹具全部来自本机想象

- 本机：Win11 build 26200 + 微信 4.1.13.65 + DPI 120 + UIA 正常
- 故障机：Win10 19042/19045 + UIA **空控件树**（descendantCount=0）+ OCR 拆词 + PowerShell 10s 级卡顿
- 所有 headless 故障注入的夹具，都是"开发方猜测故障机长什么样"构造的——**猜对才测得到，猜错测了也白测**
- self_check 文件巨大（active_touch 目录下 self_check 合计 600KB+），绿得很壮观，但对异机失败没有预测力

### 根因 3（流程层）：诊断数据链断裂，修复是在盲猜

`desktop/src/shared/wechat-window-diagnostics.cjs:8` 注释原文：*"A fixed technical schema: no window captions, contacts, paths or raw stderr."*

- 白名单只允许：阶段枚举（:1-3）、数值计数器（:4-6）、净化后的窗口类代码（:30）
- **没有**：OCR 实际读到的文本、候选控件的几何信息、失败瞬间的画面
- 后果：开发方收到 `search_result_identity_unverified`，无法区分是 UIA 空 / OCR 拆词 / 多候选 / "搜一搜"混入中的哪一种——只能靠用户口头描述和运气
- PROJECT_STATUS 1.1.21 条目自己承认："历史日志吞掉了底层异常，无法进一步区分"

**隐私白名单本身是正确取舍（客户运营工具上传聊天原文是自杀），问题在于没有"用户主动提供证据"的补偿通道。**

### 根因 4（编排层）：停机范围过粗，单点故障放大为全局停摆

`desktop/src/main/wechat-workflow.cjs:375-388`（`applyTaskAttention`）：

```javascript
if (!requiresGlobalAttention && LOCAL_TASK_ATTENTION_REASONS.has(reasonCode)) {
  return;  // 白名单内：只停本任务
}
enabled = false;          // 白名单外：停掉整个微信调度器
phase = "needs_attention";
```

- 白名单外**任何** reasonCode → `enabled=false` → 朋友圈、自动回复全部陪葬（:384-387）
- runCycle 捕获异常同样全局停（:509-516）
- `integrity_error` → `canRetry` 恒 false（touch-workflow.cjs:176, 442）→ **永久卡死，唯一出路是"添加新任务"**
- 默认方向反了：**未知原因码应该默认只停任务，全局停才需要进白名单**。现在的实现是"未知的都按最危险处理"，在故障机上每个新形态都是"未知原因"，于是用户反复看到"全部停止"

用户体感由此而来："刚开始就停""无法持续"（1.1.24 条目原话）。

### 产品层：没有降级通道，全部压力压在"自动核验必须 100% 成功"上

- fail-closed 原则本身正确（发错客户比不发严重 100 倍），不可动摇
- 但产品形态上，核验失败只有两条路：机器自动恢复（2 次）→ 任务停。**没有"我在微信上亲眼确认了就是他，继续"的人工旁路**
- 1.1.20 的 `45/3583` 揭示了另一个产品事实：**3583 人的批量规模下，单点成功率 99% 也意味着 35 个人出问题**。没有批量容错设计（失败重排队、批量终态报告、分批确认），用户就必须全程盯盘
- 用户的目标（跑完这批人）和系统的行为（每步完美核验，不完美就停）之间存在结构性张力——这不是 bug，是产品定义缺口

## 四、方向有没有走偏？

**没走偏、必须坚持的部分：**

1. fail-closed 发送原则：`outcome_unknown` 不重发、`send_attempted` 后不重试、已确认发送的分段不重复——这是产品生命线，宁可不发不能错发。**不要"加固"它，也不要为走通链路软化它。**
2. 隐私诊断白名单——方向正确，缺的是补偿通道（见建议 4），不是放开采集。
3. 业务状态分离架构（contact_sync / active_touch / auto_reply / moments 账本隔离）——是对的，1.1.26 的任务隔离修复也在正确方向上。
4. 人工决议机制（resolve-unknown 三选一）——设计完整，是好资产。

**走偏的部分：**

1. **把环境适应问题当逻辑 bug 修**——7 个版本加启发式分支，分支空间不可枚举，永远修不完。
2. **把测试绿当成进展**——夹具来自猜测而非现场，"故障注入通过"≠"问题解决"。版本号在涨，闭环一个没有。
3. **迭代节奏错配**——一天 5 版 vs 用户几天测一次，修复堆积在"待验收"，没人知道哪个真有效；且多版本叠加后，故障机新反馈甚至无法归因到具体哪笔修复。
4. **全局停机放大了单点故障的体感**——一个人核验失败，朋友圈和自动回复一起停，用户觉得"整个软件都是坏的"。

## 五、改善建议（按优先级）

### P0：本周就该做（止血）

**1. 反转停机默认值。** 未知 reasonCode 默认只停当前任务，全局停改为显式白名单（仅限：结果不明 `outcome_unknown`、授权失真、完整性错误、窗口/账号身份丢失）。一行判据：**这个错误值得让朋友圈和自动回复一起等吗？**

**2. 给 `integrity_error` 一条出路。** 永久卡死状态必须有"重置此任务（丢进度重来）"入口。用户可以接受丢进度，不能接受死锁。

**3. 停止盲发版本。** 精准触达的新修复，在故障机验收闭环前不累计第二个版本。把 1.1.27 的验收做完再动下一刀。版本号膨胀正在掩盖"没有闭环"这个事实，并且让归因变得不可能。

### P1：两周内（打破盲修循环）

**4. 做"现场证据采集器"，补上诊断链的断口。** 隐私白名单不动，但加一个用户主动触发的"诊断快照"：身份核验失败瞬间，本地保存（不上传）打码截图 + OCR 原文 + 候选几何 JSON，用户一键导出/发送。把"我要证据你不给"改成"需要证据时教你采"。这一步直接决定根因 2、3 能否解开。

**5. 加人工确认旁路，给系统降级通道。** 核验失败时给用户第三个选项："我在微信上确认了就是他 → 本次继续发送"。fail-closed 的对象从"整个流程"收窄到"发送动作本身"（发送前复核、发送后确认维持原样不动）。这把"自动核验 100% 成功"的不可能目标，变成"自动为主、人工兜底"的可达目标。

**6. 建"故障机形态库"。** 每次采回来的真实形态（截图+OCR+几何）固化为离线测试夹具入库。测试的目标形态从"本机猜的"换成"现场采的"，headless 测试才开始有预测力。

### P2：结构性（一个月内，产品经理要拍板）

**7. 核验策略重构：从"认出好结果"转向"后验验证"。** 现在的策略是在搜索结果页识别哪个候选对——识别问题不可枚举。反过来：点击前记录会话快照，点击候选后核验会话身份（标题/微信号区域比对），错了退回搜索页标记该候选不再点。把"识别问题"变成"验证+回退问题"，后者的形态空间小得多、且可利用已有的会话核验资产。点错成本由"会话快照比对"兜底，不触碰发送安全线。

**8. 对"无 UIA 机器"做产品决断。** Win10 19042 上 UIA 恒为空时，OCR 路径的可靠性天花板可能撑不起全自动。拍板选项：(a) 这类机器走半自动模式——人点搜索结果，机器管话术、节奏、账本；(b) 列为不支持环境并明确告知。硬撑全自动 = 无限打地鼠，且每一版都在消耗用户信任。

**9. 为批量规模设计容错。** 3583 人规模下小概率故障必然发生：失败联系人自动重排队（限次）、批量终态报告（成功/跳过/待人工分列，1.1.26 已开始做）、分阶段自动续跑。验收标准从"一个人都不出问题"改为"出了问题用户不用盯"。

### 给产品经理的一句话

现在的问题不是"还差几个版本能修好"，而是**当前形态下"修好"不可达**。止血（P0）解决用户体感，证据链+人工旁路（P1）解决修复效率，策略重构+环境决断（P2）解决根因。三层都要做，但顺序不能倒——先让用户不再"动不动就全停"，再让自己看得见故障现场，最后才谈根治。
