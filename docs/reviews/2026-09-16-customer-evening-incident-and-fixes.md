## 一、先说结论：不是"bug 越修越多"，是同一条老根因在新模块上重演

客户机日志统计：**昨晚一共有 16 次"全局停机"**，每次都要人手工点一下才能继续：

| 停机原因 | 次数 | 发生在 |
|---|---|---|
| message_snapshot_unavailable | 5 | 文本消息发送 |
| wechat_window_not_foreground | 5 | 22:58–23:39（用户自己正在用微信） |
| image_driver_failed | 2 | 图片发送 |
| image_draft_format_unavailable | 1 | 图片发送 |
| image_existing_draft | 1 | 图片发送 |
| task_needs_attention（超时） | 1 | 图片发送 |
| atomic_send_not_verified | 1 | 文本消息发送 |

**新加的图片功能没有问题，问题是图片功能的每一个失败码都自动继承了"失败 = 全局停机"的老默认值。** 用户看到"新 bug"，实际是同一条放大链开到了新路上。2302 人的任务，昨晚只推进了不到 20 人。

另外一个必须说的发现：**客户机跑的版本里已经带着今晚 Codex 未提交的埋点代码**（failure-evidence 目录、rule_id 都在工作）——也就是说未经提交验证的 WIP 已经打包发给客户了。这本身就是"越修越多 bug"的流程性根源。

三个今晚特有的新问题，逐一给方案：

### 问题 1：图片发送的三个失败全是"可恢复"的，却全部全局停机

- 21:58 的 image-r005 和 22:18 的 image-r010，`sendAttempted=False`——**系统明确知道还没发送**，却把整个任务停了。
- **修复**：图片失败码并入方案 A 的分级表：凡 `sendAttempted=false` 的图片失败（image-r001~r010）→ 重试 2 次 → 仍失败跳过此人、记入"未触达名单"。`powershell_timeout` 同理（未确认发送与否才需要标记 outcome_unknown，但**任务仍应继续**）。

### 问题 2：用户正在用微信 = 必然停机，这是和产品定位冲突的致命设计

客户用电脑工作时微信就在前台——RPA 每个 worker 都要求"微信前台 + 键盘鼠标空闲"，抢不到就 `wechat_window_not_foreground` 停机。**用户越用，停得越多**。昨晚 22:58–23:39 连续 5 次就是这么来的。

- **修复（立即）**：`wechat_window_not_foreground`、`wechat_user_active`、`wechat_external_input_detected` 三兄弟归入"环境类"——**任务挂起等待 + 轮询重试（每 30 秒试一次，最多等 10 分钟）**，人一离开自动续跑；等待期间 UI 显示"检测到您在操作电脑，任务已暂停，离开后自动继续"。绝不停机、绝不要求人工点按钮。
- **修复（中期，方案 B）**：支持后台窗口模式（UAIA 可以对非前台窗口 SendInput 改用 UIA ValuePattern/SetForegroundWindow 短暂切换），把"必须独占前台"的门禁降到只在点击和发送前 0.5 秒要求。

### 问题 3：英文错误码裸露给客户（"原因未提供"雪上加霜）

截图里客户看到的是「[wechat_window_not_foreground] 原因未提供」。渲染层想查中文映射表，但映射表没收录这个码，于是把原始码打了出来，还附了一句"原因未提供"。

- **修复**：① 建一张 reason_code → 中文文案的全量映射表（以 `wechat-rule-catalog.json` 的 391 条为准生成，缺省兜底文案"操作未完成，已自动重试/已跳过，稍后自动继续"，**绝不显示英文码**）；② 加一条自检：凡是 UI 能收到的 reason 码必须在映射表里，否则构建失败。

### 问题 4（附带）：图片脚本 30 秒超时在客户机上太紧

客户机慢（Win10 + 老配置），图片脚本含剪贴板重试后 30 秒可能不够。超时后 sendAttempted 未知 → 只能标"结果未确认"。

- **修复**：超时提到 60 秒；更重要的是把"点击发送按钮"之前和之后分成两个进程阶段——**超时发生在点发送前 → 明确"未发送"可安全重试；发生在点发送后 → 保持"未确认、不补发"**。现在的单脚本结构把两种情况混在一个超时里。

## 三、给 Codex 的修复指令（按顺序，一次一档）

**第 1 档（明天上午，改动最小、客户感知最大）：**
1. 停机白名单扩充为分级表（最小版）：`wechat_window_not_foreground` / `wechat_user_active` / `wechat_external_input_detected` → 挂起等待自动续跑；所有 `sendAttempted=false` 的图片/文本失败码 → 重试 2 次 → 跳过此人继续。两条编排路径（touch-workflow、touch-task-ipc）同步改。
2. 错误码中文映射表 + 自检，UI 禁止裸码。
3. 图片发送超时 30s → 60s。

**第 2 档：** 图片发送脚本拆"点击前/点击后"两阶段，超时按阶段定性（未发送 vs 未确认）。

**第 3 档：** 前台依赖降级（只在点击/发送前要求前台，其余阶段后台化）+ 方案 B 的常驻进程提速。

**流程纪律（必须执行）：**
- **未经提交、未过自检、未真机验收的构建严禁发给客户**。昨晚客户机上的 WIP 版本就是反例——这也让"分不清哪版引入的 bug"雪上加霜。
- 每档改动单独 commit + 单独打包版本号，客户机验证通过再发下一档。

**验收标准**：模拟"用户全程正常使用电脑"场景跑 50 人任务，要求零人工干预完成率 ≥ 90%，失败者全部进入可重跑的"未触达名单"；UI 全程无英文错误码。
