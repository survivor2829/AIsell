## 一、核心判断（请优先核验这一条，它决定后面所有工作的优先级）

**高置信，基于客户机日志实证**：昨晚客户机全局停机 16 次（snapshot×5、window_not_foreground×5、图片类×4、超时/atomic×2），2302 人任务推进 <20 人。根因不是图片模块的新 bug，而是**"任何失败码 → 全局停机"的编排默认值**在新模块上重演。391 个 rule_id 埋点已生效，但编排层尚无任何代码消费这些编号做"重试/跳过/挂起"决策。
—— 请核验：你是否有我不知道的设计理由，让部分失败必须全局停机？若有，列出清单，其余并入分级。

## 二、修复指令（三档，一次一档，每档独立 commit + 独立版本号）

**第 1 档（止血，改动最小）**
1. 失败分级决策表：391 个 reason_code / rule_id 分三类——
   - 环境类（`wechat_window_not_foreground`、`wechat_user_active`、`wechat_external_input_detected`）：挂起等待，30 秒轮询，人离开自动续跑，**不停机、不需人工点击**；
   - 可恢复类（所有 `send_attempted=false` 的图片/文本失败码、`input_draft_read_failed`、`wechat_target_changed`、`search_result_identity_unverified` 等）：重试 2 次 → 仍失败跳过此人，任务继续，进"未触达名单"可二次执行；
   - 阻断类（发送动作可能已发生、结果未知）：标记 `outcome_unknown`，**不补发**，跳过此人，任务继续。默认规则：**未知错误码 = 可恢复类（跳过继续）**，只有显式列入阻断类才升级。
   - 注意：`touch-workflow.cjs` 与 `touch-task-ipc.cjs` 两条路径必须同步改（历史上多次只改一处导致行为不一致）。
2. 错误码中文映射表：以 `wechat-rule-catalog.json` 生成全量映射，UI 禁止裸露英文码（昨晚客户看到"[wechat_window_not_foreground] 原因未提供"）；缺省兜底文案 + 自检（UI 可收到的码必须命中映射表，否则构建失败）。
3. 图片发送脚本超时 30s → 60s。

**第 2 档（定性准确）**
4. 图片发送脚本拆"点击发送前 / 点击发送后"两个阶段：超时或失败发生在点击前 → 明确"未发送"可安全重试；发生在点击后 → 保持"未确认、不补发"。当前单脚本把两种情况混在一个超时里。

**第 3 档（安全与性能，放量千级前必须）**
5. 认人强比对：`identity_relaxed` 路径补"标题精确匹配 / 头像区域哈希 / 微信号字符串比对"三选二，不满足 → 跳过此人而非点击。千人规模 1% 错点 = 10 个发错人且显示成功。
6. 发送前草稿核验 UIA 直读优先（零剪贴板依赖），坐标+剪贴板降级保留；禁止"跳过发送前核验"的捷径。
7. 常驻 PowerShell 会话：每联系人 6–10 次调用（每次冷启动 + Add-Type 编译 0.5–1.5s）合并为 1 个常驻进程，Win32 类只编译一次；合并同一秒内重复的窗口身份/前台焦点核验；固定 sleep 改轮询事件。目标 32s → 10–15s/人。
8. 诊断事件补版本号 + git 短哈希（消除"分不清哪版引入"的盲修）。
