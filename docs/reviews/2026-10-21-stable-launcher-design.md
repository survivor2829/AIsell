# 稳定启动器设计（协议5，一次完整包过渡）

固定安装根的最小信任核只依赖Electron/Node内建模块、发行版标记和固定公钥配置；负责单实例、选择JSON、签名/清单结构/清单树摘要校验、boot-attempt/pending.attempted、加载及失败回退。不能先加载所选generation内的更新代码再验证其签名。启动不遍历文件内容，prepare回执与签名payload和底座身份绑定。固定核接口只有选择上下文与启动/健康确认契约；新增业务不进入固定核。

可更新updater组件负责引导、云传输、下载校验、组合、助手、备份/轮换与回执。application负责业务/界面；assets负责两个edition的图片/视频/音频/字体等静态媒体，保留原物理路径，示例媒体以STORE归档。底座只保留Electron、稳定信任核、node_modules、浏览器、media-tools、Python及第三方库；联系人助手及自身libs归入application；PyInstaller生成的归档/元数据等易变内容归对应业务组件。稳定依赖没有变化时，不因更新器变化推进底座。

update-capabilities.protocol、component-base.updateProtocol和新组件清单updateProtocol均为5；保留schema2文件描述结构。组件名新增updater、assets。新客户端可解析已发布协议4清单以比较版本，但不能与协议5底座组合；旧组件的备份引用仍按其自身组件名解析，不能因为新增组件破坏历史回退保护。服务端接受3/5技术请求头并对旧请求隐藏协议5组件，旧客户端继续读取完整包。

**旧客户端清单兼容。** 协议4客户端verifyManifest拒绝componentBase.updateProtocol=5，因此不能直接发布该字段让旧客户端自行回退。完整包公开响应保留旧格式的独立签名payload（省略可选componentBase，增加签名内componentBaseProtocol=5标记），并附加componentBaseEnvelope：对同一清单增加真实componentBase后另行签名。新版遇到协议5标记必须验证两份签名、两者除componentBase以外全部字段一致后使用补充清单；缺少扩展不能静默接受。旧版忽略新字段，仅验证旧格式payload。服务器存储原始签名响应，不按请求重签或改写payload；组件提升时验证补充清单并用其底座信息做桥接。两个清单必须绑定同一EXE摘要、大小、版本、序号和频道，不能任意拼接。仅增加响应字段与路由能力，无数据库迁移，无第二个安装器。

固定核在程序启动早期注册媒体scheme；普通启动先获取锁再写boot-attempt。助手入口从其独立运行目录加载已复制的updater，不从可被完整安装器替换的安装根执行。候选generation引导函数接受固定核已验证上下文，不再次beginBoot或获取锁；页面健康ACK仍由既有markHealthy入口完成。

| 故障 | 处理 |
|---|---|
| 签名/清单错误、updater入口缺失或加载抛错 | 拒绝候选，更新selection回上一generation，必要时回安装自带版本，并给出恢复提示 |
| 新版首启崩溃、无健康ACK | 下次启动pending.attempted/boot-attempt触发回退，不改用全量哈希重试 |
| 下载字节篡改 | 一次下载SHA-256失败即拒绝，不能生成prepare回执 |
| 补充清单签名错误或与旧格式清单不匹配 | 新版拒绝完整更新，不容错拼接；旧版只消费其原本能验证的旧格式payload |
| 回收被占用或证据不足 | 保存原因和引用，下次后台重试；不把历史未登记目录接管为垃圾 |

固定核只有在信任格式、启动契约、Electron基础能力或公钥迁移时才升级；更新器、传输、备份、素材与普通业务变化均走组件。协议5过渡安装一次完整包，后续分别用更新器增量和界面增量验证不再全量、界面不下载assets。执行前完成独立只读设计审查；运行时和真实升级分别验收。

独立审查已完成并采纳：引导抛错后的回退必须先保存选择再干净进程重启，最多上一代→安装自带两次，避免复用已污染的IPC/监听器；助手执行文件和加载的DLL独立复制一次，不与被安装器替换的安装根共享硬链接；补充签名payload及核验出的真实底座进入读回/升级路径缓存身份，缺失或替换不可报告核实成功；发布读回也必须声明协议5，旧请求3（包括Bridge-Update=1）必须隐藏六组件清单；保留generation版本不高于安装版时回到安装自带版本的现有规则。
