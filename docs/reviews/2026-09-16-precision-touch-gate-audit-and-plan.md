## 一、Codex 今晚（20:22–23:27）那批改动到底是什么

工作区共 **19 个修改文件 + 7 个新文件，约 765 行新增**。逐个 diff 读完后，结论一句话：

> **这批改动是"给每个安检口装监控摄像头"，不是"拆多余安检口"也不是"修发动机"。方向对，但只解决了"看不见失败在哪"，没解决"跑不通"和"卡"。**

具体分三部分：

1. **失败证据系统（占 90%）**：新文件 `failure-evidence.cjs` + `wechat-rule-catalog.json`。给全项目 **391 个失败分支**逐一编号（窗口类 45 条、真实发送类 33 条、朋友圈导航 87 条、wx4/wx5 共 188 条、图片 14 条、搜索认人 15 条、草稿 9 条）。今后每次失败会落盘一条 JSON（规则编号 + 原因）+ 一张完全遮蔽内容的截图，最多保留 50 条。**纯诊断，不改任何行为。**
2. **少量真实修复（约 150 行）**：剪贴板被其他程序占用（COM 错误 0x800401D0）时自动重试 5 次；发图片前如果输入框有残留草稿，先清空并验证清干净；用剪贴板序列号判断复制是否真完成，替代死等 120ms。
3. **诊断链路补全**：把之前"日志黑盒"的几个口子补上（搜索认人失败现在带 rule_id 和候选数、图片发送带阶段编号）。

**评价**：质量不错，遮蔽隐私做得严谨（截图连内容都盖住只留 2 像素边框），重试是修真问题。但它只是仪表盘——下面这些真问题一个都还没动。

## 二、通俗讲：这条链路现在为什么"跑不通 + 卡"

把一次精准触达想象成**让一个访客过 8 道安检口**：

> 准备窗口 → 搜索联系人 → 认人（搜索结果核验）→ 点人 → 会话核对 → 输入文案 → 发送前核验草稿 → 发送并确认

8 道口子后面共埋了 **391 条小门禁**。门禁本身不是坏事——发错人、重复发送是事故，宁可严格。但现在的设计有三个结构性问题：

### 问题 1（最致命）：任何一条门禁失败 = 全车掉头回家

391 条门禁里，**绝大多数失败都会把整个批量任务打断**，只有少数在白名单里。这就像机场安检：一个人包里有瓶水（倒掉就行、人可以走），结果直接把整架航班停飞。

- 千人任务按 95% 单人成功率算，**预期失败约 50 次 = 停机 50 次**，每次都要人守着点继续。这就是"跑上百成千个联系人"做不到的第一原因。
- 本机今天就是活案例：13:50–14:34 三轮任务 20 次失败没停机（认人类已在白名单），但一次 `wechat_target_changed` 就全局停了 29 分钟。
- **讽刺的是**：Codex 今晚花 3 小时给 391 条门禁装了编号，但**编排层还没有任何一行代码去"读"这些编号来决定"重试 / 跳过 / 停机"**——摄像头装好了，指挥中心还没接电。

### 问题 2（"卡"的主因）：每过一个口子都重新办进馆证

每个安检口都是一个**新开的 PowerShell 进程**，一次触达约起 6–10 个。每个新进程都要**从零编译一遍 C# 的 Win32 类**（Add-Type），还要加载 .NET。粗算：

- 每个进程冷启动 + 编译 ≈ 0.5–1.5 秒 → 每个联系人 **3–10 秒纯开销**
- 再加上代码里到处是固定 sleep（120/300/350ms）、空闲租约检查、剪贴板备份恢复
- 实测 32 秒/人，**估计一半以上是重复开销，不是真在干活**

而且同一个东西被反复验：窗口身份在 8 处验、前台焦点验 10+ 次、一秒内同一窗口反复确认。**门禁数量过多 + 每条门禁的执法成本过高，两件事叠加。**

### 问题 3（没做到位的三件事）

1. **认人放宽了但没配强比对（安全债，放量前必须还）**：1.1.31 为了通过率把认人放宽成"唯一候选就点、标题包含就算验证"。千人规模下 1% 认错 = **10 个人收到发错的私信，且系统显示"发送成功"**。这是唯一可能造成客诉/封号级事故的点。
2. **发送前草稿核验仍以"坐标点击 + 剪贴板 + Ctrl+A/Ctrl+C"为主**，UIA 能直读草稿却不用。剪贴板是全系统最脆的部件（被输入法、其他程序一抢就崩），能绕开就绕开。
3. **日志没有版本号**：失败日志分不清是 1.1.30 还是 1.1.33 跑出来的。这就是 Codex 反复盲修的机制性根源——他在修一个可能已经不存在的 bug。

## 三、改进方案（给 Codex 的执行顺序）

### 方案 A：接通"指挥中心"——失败分级决策表（第一优先，工作量约 1 天）

391 个 rule_id 已经打好，现在按后果分三类，写进编排层：

| 分类 | 判定 | 处置 | 例子 |
|---|---|---|---|
| **阻断类** | 发送动作已可能发生，结果未知 | 停此人，**标记 outcome_unknown，不补发**，任务继续下一个人 | `wechat_send_point_obscured`（点击后失焦） |
| **可恢复类** | 明确还没发送 | **自动重试 2 次 → 仍失败则跳过此人，任务不停** | 认人未确认、`input_draft_read_failed`、窗口未就绪、`wechat_target_changed` |
| **环境类** | 人正在用电脑 / 微信掉登录 | **暂停任务挂起等待**（不终止），人离开后自动续跑 | `wechat_user_active`、`wechat_login_required` |

- 白名单思路（从"少数放行"改为"少数拦截"）：**默认一切未知错误 = 跳过此人继续**，只有阻断类才停。
- 改造点：`touch-workflow.cjs` 与 `touch-task-ipc.cjs` **两条路径必须同步改**（此前多次只改一处导致行为不一致）。
- 验收标准：**模拟 10 次失败注入，任务零人工干预跑完，失败者进入"未触达名单"可二次执行。**

### 方案 B：提速一半以上——办一次证用一整天（第二优先，工作量约 1–2 天）

1. **常驻 PowerShell 会话**：一个联系人的 6–10 次调用合并进 1 个常驻进程（`-EncodedCommand` 连续投喂，或改用单脚本内分阶段执行），Win32 类只编译一次。预计 32s → **10–15s/人**，千人从 20 小时降到 6–8 小时。
2. **合并重复核验**：窗口身份 + 前台焦点在同一秒内只验一次；非关键步骤（读会话列表等）去掉空闲租约强制检查，只在**点击和发送前**强制。
3. **sleep 换事件**：固定 350ms 改为轮询 UIA 属性变化（最长等 1s，变化即返回），大部分情况能提前返回。

### 方案 C：补上没做到位的（放量前必须完成）

1. **认人强比对**：`identity_relaxed` 路径必须补"标题精确匹配 + 头像区域哈希比对 + 微信号可见时字符串比对"三选二，不满足降级为"跳过此人"而不是"点击"。
2. **UIA 直读草稿优先**：发送前核验先试 UIA 读输入框文本（零剪贴板依赖），失败才降级到现有坐标+剪贴板方案。禁止任何"跳过发送前核验"的捷径。
3. **日志带版本号**：每次诊断事件写入当前 app 版本 + git 短哈希，从此不再盲修。

### 方案 D：流程纪律（Codex 工作方式约定）

1. **今晚的 WIP 先独立提交**（纯诊断埋点一个 commit，剪贴板修复一个 commit），不能和行为修复混在一个大包里——混包是"打包→出 bug→查不清是哪改的"循环的直接原因。
2. **一次只改一个方案字母**，改完在真机跑 20 人验证，通过再下一个。
3. **验收协议**：客户机先复验 1.1.33（不动代码就能确认剪贴板修复是否生效）→ 方案 A 后跑 100 人两批全绿 → 方案 B/C 后再放量千人。

### 你需要拍板的三件事

1. 客户机 3583 人里**没公开微信号的会被自动排除**，实际可跑数可能远小于 3583——要不要在跑前加一个"可触达人数统计"页？
2. 即使提速后，千人仍需 6–8 小时且**期间不能碰电脑**（门禁要求独占输入）——要不要做"半自动模式"（UIA 失效时人工确认一次，跳过自动认人）作为兜底？
3. 1.1.31 放宽认人后已发的那些消息，有没有客户反馈发错人的？有的话方案 C1 优先级提到最高。

## 四、一句话总结

**不是推倒重来，也不用再"反复搭建"。门禁体系（391 条规则 + 今晚的证据系统）本身是好资产，缺的是三样：① 让失败可恢复而不是全局停机（接通指挥中心）；② 让门禁执法成本降下来（常驻进程，提速一倍）；③ 把认人强比对和 UIA 直读补上（安全 + 稳定）。按 A→C→B 的顺序做，三轮内"千人可跑"是现实目标。**
