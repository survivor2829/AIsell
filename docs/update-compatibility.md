截至本补充，排除再生运行链接、保留业务目录链接及核对链接目标的修复已进入本轮开发分支，**未打包交付，未证明客户电脑恢复更新**。有签名 v1 完整包且下载摘要正确，只证明制品可获取；不能据此认定旧端备份、安装、启动确认与数据保留均可走通。

旧客户端请求固定的无参数 v1/v2 `latest`，不携带版本或底座标识；单份 v2 清单又严格匹配一个底座指纹。因而服务端不能据此可靠地同时分流多个旧底座。旧端还要求 v2 版本不低于 v1，桥后最终完整包须有更高版本。当前已实现固定旧协议路由和1.1.58底座桥接源码，仍需以原制品、普通用户权限和含真实 junction 的隔离资料目录完成端到端升级证明；其他旧底座不能借用此结论。以下保留既往验收记录，不将其扩展为全部历史版本已通过。

### 新客户端发布路由能力（待发布）

客户端只在现有 v1/v2 `latest` 请求附带以下技术信息；安装包下载、诊断上报不携带这些路由头：

| 请求头 | 值与用途 |
| --- | --- |
| `X-Xiaoxi-Update-Protocol` | `3`，识别具有路由能力的新客户端 |
| `X-Xiaoxi-Version` | 当前运行的三段业务版本；组件更新后使用实际运行版本 |
| `X-Xiaoxi-Base-Version` | 当前 `component-base.json` 的底座版本；无有效底座时省略 |
| `X-Xiaoxi-Base-Fingerprint` | 同一底座的64位十六进制摘要；无有效底座时省略 |

这些头没有账号、安装ID或本地路径，只用于选择发布物，不能作为权限或可信版本证明。签名、频道、单调序列号、版本比较及底座摘要兼容校验仍由客户端执行。服务端升级前忽略这些头即可维持现有行为。

维护服务已实现显式启用的固定旧协议路由：无能力头返回固定旧版 v1/v2 配对，协议3请求读取通常的 latest；配置、签名、制品或包内最终目标不符时拒绝放行。它不会按IP、版本猜测或轮换响应选择旧底座，尚未部署或启用。发布前校验读取真实 application ZIP 的 `files/resources/app/src/main/legacy-update-target.json`；构建产物边界检查已通过。配置与启用门槛见 [服务路由说明](../server/maintenance/legacy-releases.md)。

### 1.1.64 过渡包交付门槛

当前已验证源码、底座、桥接协议与隔离恢复流程，尚未取得故障电脑的原程序证据。不能把新版本里的备份修复当作旧版运行中助手的修复。隔离桥接保留原1.1.64应用依赖，只替换经过核对的补丁；不得把当代应用直接放到1.1.58底座上。

桥接版本须高于原版，且不低于无路由头客户端同时收到的v1版本；最终完整包须高于桥接版本，并在这轮更新开始时固定签名目标。第一段组件更新本身不执行旧助手的业务备份，因此可用于投递修复。第二段需验证实际助手已加载修复、仅延续本次更新授权、普通退出不安装、备份失败不触碰安装目录，以及启动确认/恢复。原1.1.64助手尚无新助手的提交握手及程序回退能力，不能只改一处备份过滤就写成完整连跳已通过。

2026-10-12只读核对：服务端 `/var/lib/ai-maintenance/releases/test` 当前保留的历史签名清单未发现版本1.1.64；本地已留存1.1.58底座，但本次未取得可核验的原1.1.64完整应用制品。用户确认故障电脑仍是1.1.64且能正常打开；已提供[只读采集程序](legacy-update-evidence.md)，等待返回应用版本、组件清单及程序摘要/对应文件，再核对实际补丁适配并完成隔离两段升级。采集不包含业务资料，也不能单独充当完整可运行安装制品。该缺口不要求客户删除业务数据或反复覆盖日常安装。

## 发布顺序

1. 在干净、已验收的同一版本提交构建并发布完整安装包，保留现有客户公告、签名、版本和提交检查。
2. 再发布增量包。门禁读取同频道 v1 签名清单，要求版本与本次目标完全相同；实际下载完整包并核对摘要及大小。缺失、旧版本、损坏或不可访问均阻止增量发布。
3. 上传完成、切换增量清单之前再次读取 v1，防止发布途中目标变化。服务端 `promote_components.py` 在 v1/v2 共享发布锁内再核对版本与完整文件哈希，消除最后一次读回与切换之间的并发窗口；此门禁需要随维护服务部署，本轮源码修改不表示已经部署。升级支持起点由 `desktop/release-upgrade-support.json` 维护；新起点需先核实协议，不能仅加版本号。

1.1.78/79 当时选择同目标完整包作为旧协议过渡路径，未实现依赖多次重启的中间版本连跳。客户端仍优先下载适用的增量内容；不兼容时选择完整包的协议行为，受本页顶部已确认的旧端备份缺口限制。保留 1.1.57 等旧底座支持期间，每个版本需构建并上传完整包，发布端还会下载一次校验，增加发布耗时和流量；不能通过删除支持起点绕过客户的升级路径。

`src/main/cloud-release-config.json` 通过 `build-portable-release.cjs` 的 src/main 递归复制进入安装版；测试、正式配置独立，正式频道默认禁用。启用正式频道前必须填入可信域名、公钥并建立该频道的已核实升级起点，发布脚本目前仍只发布测试频道。
