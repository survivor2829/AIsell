# 内部更新标准

适用范围：开发者电脑及已安装测试版的内部测试用户。正式客户频道继续关闭。当前流程使用 GitHub Actions 做 CI，受控 Windows 构建机做打包和 CD；签名私钥与服务器 SSH 凭据留在构建机，不进入 GitHub 工作流或安装包。

**默认采用组件增量更新。** `release:internal` 与 `publish:internal` 两个日常入口在 `package.json` 中固定传入内部增量默认标记，底层脚本无参数时也保持增量默认；明确的 `release:components`／`publish:components` 入口仍只允许组件包。用户仍通过同一个“检查更新”入口操作，客户端下载有变化的组件。只有明确传入 `--full`，或增量兼容门禁确认底座／数据模式不兼容时，才允许改走整包；首次安装或明确需要离线安装器也使用该显式入口。改动数量多、普通构建失败和操作习惯都不是改走整包的依据。

**客户交付制品标准。** 客户验收和覆盖安装统一提供安装程序（`AI获客 V1.0版本-安装程序.exe`）及同版本清单；便携 ZIP 不作为客户交付制品。ZIP 或解压目录若因构建链需要产生，只能留作本机中间产物，交付前不得打包给客户。

## 每次更新的固定顺序

用户 2026-10-11 确认：采用本机定向验收 → CI → 合并 main → 内部 CD。虚拟机、另一台电脑及新增候选频道不作为每次发布前提；微信或 Windows 适配变更按实际风险补兼容验证，未验证范围单独记录。正式客户频道和付费搜索仍关闭。历史验收记录保留当时结论，不构成当前额外发布门槛。

1. **完成改动与本地功能验收。** 更新版本号、具体更新说明和 `PROJECT_STATUS.md`，核对需要同步部署的服务端接口。先在本地候选安装版通过软件入口验证本次核心功能与历史数据保留，不以脚本单独运行或构建通过替代；在此之前不推送触发 CI。只提交本次确认的源码和文档，保留原素材、用户数据及回滚证据。
2. **验收通过后运行 CI 并合入 main。** PR、main 推送或手动触发 `Windows CI`，功能分支普通推送不再额外跑一套重复检查。现有并行作业检查 Node/Electron 源码契约、维护服务、供应商网关、确认稿制作、制作聚合及请求用量，并构建测试/交付界面。失败先修复，审查通过后合入 main；若应用内容变化，复验受影响功能。CI 不访问真实微信、不调用付费生成、不读取发布私钥，也不发布客户更新。
3. **构建候选版本。** 日常从同一干净提交执行 `release:internal`，默认只构建增量；`release:components` 是同一路径的兼容入口。首次用 `--base` 指定已验收的完整测试版目录并成功构建后，本机构建记录会记住该底座，后续默认继续使用，不再回退到旧候选。候选须与该底座兼容；不兼容时列出变化的基础文件，由实际差异判断是否需要显式 `--full`，不自动生成大包。UTF-8 文本只有 CRLF/LF 表示不同而内容相同时沿用已验收底座字节；真实文本变化和二进制变化仍严格拒绝。三个大型运行时按源码、构建工具、依赖及许可输入指纹复用；Python 库内容逐项相同时沿用已验收压缩包，避免文件顺序改变底座摘要。真实依赖变化保留新内容。两种路径均执行发布检查和组合后的应用校验，界面构建不能替代运行时验证。
4. **本机升级验收。** 保存编辑内容并结束任务，正常关闭应用。组件验收使用 `npm.cmd run backup:local -- --program <原安装目录> --profile <该edition用户目录> --output-root <备份目录> --purpose acceptance --update-kind components`：记录当前选择，使用更新器的当前／上一代指针回退，不复制业务资料。完整升级将 `--update-kind` 改为 `full`，开发机备份统一放在 `D:\OpenAI\LocalInstallBackups\<edition>`；内容摘要一致才复用。新版启动与业务数据检查通过后，受管自动／验收备份只保留最近一代；用户主动备份（默认 `--purpose manual`）、未确认失败证据和历史未分类备份不自动淘汰。不要逐版本人工复制整个用户目录或创建 `.local-rollback-*` 副本。增量候选组合目录保留在构建记录的 `candidateRoot`，验证实际下载、切换、启动和数据保留；整包候选执行覆盖安装。核对版本/构建号、图标、登录、配置、历史及本次关键功能。升级检查不授权真实微信发送或新的付费调用。
5. **部署依赖服务。** 新客户端依赖新增接口时，先按维护服务说明备份数据库、部署同版本服务文件，验证健康和明确的测试记录闭环，再发布客户端更新。
6. **发布已验收的同一版本。** 校验实际产物与清单一致，默认用 `publish:internal` 发布增量；整包必须显式指定 `--full`。原 `publish:components` 入口仍可使用。不得在验收后重新构建另一套产物直接替换。1.1.0 起后台准备更新，用户在顶部“检查更新”中明确选择更新后才退出安装；普通退出不自动安装。独立更新窗口等待相关工作进程退出后切换，启动成功才显示完成。旧 1.0.2 保持其原有更新行为，由过渡安装器显示安装过程。
7. **核对发布结果。** 发布脚本在上传与服务器切换完成后，自动从对应的 `/v1/releases/{channel}/latest` 或 `/v2/releases/{channel}/latest` 端点只读获取清单，沿用客户端 HTTPS、CA、超时及响应大小限制，验签并与本次提交的 payload 完整比较，覆盖版本、序号与全部制品摘要；无需重新下载大型组件。读回未核实时命令返回失败，明确提示“发布可能已完成”，不得直接再次发布；保留原版本和序号，只查询原端点核对。核对本机最新安装版，记录成功与未验收项。内部同事的电脑是否已完成安装，以该电脑状态或收到的运行记录为准，不能把服务器发布成功写成所有人已更新。

日常使用只需说清“本机验收通过，发布内部更新”。已有授权且版本与范围不变时，继续完成后面的步骤，不为每个命令重复询问；正式客户发布、额外付费调用、新增真实微信操作或重要数据清理仍按对应范围处理。

## 构建与发布命令

在 `desktop/` 执行。首次配置构建机时，参考 `build/internal-release-config.example.json`，将实际已有 Python、FFmpeg、Chromium 和对应来源记录的路径保存到 `.build/internal-release-config.json`。相对路径相对于配置文件所在目录；不要把密钥放进此文件。环境准备与安装依赖不是每次更新的重复步骤。

**开发发布提速（2026-10-21）。** 干净HEAD对应的main推送Windows CI两个源码作业及`Product detail local E2E`步骤均成功时，发布复用该run的源码/E2E证据，并将run id写入构建与空间记录。旧CI缺少E2E、提交不一致、查询失败或工作区不干净时不能跳过；`release:internal -- --force-checks`强制本地检查。运行时清洁门禁、包验收、隐私扫描、发布前归档摘要和读回验签继续执行。

Python构建指纹按解释器/DLL、包版本、requirements和显式运行时配方版本计算，同一次发布共享环境探测；缓存实现和回执脚本变化不会单独重打运行时。不可变运行时缓存到暂存目录同盘优先硬链接，候选程序仍为独立副本。构建内复用带文件身份和时间戳的摘要清单；归档流式写盘，压缩媒体使用STORE。上述复用不提供检测保持元数据不变的任意外部篡改的保证。CI纯文档提交跳过源码作业；自检进程数默认不超过6，独占资源检查串行。

```powershell
npm.cmd run release:internal
```

默认产物为 `release/components/test/unsigned-component-release.json`、四个按哈希命名的组件归档及已验证的候选组合目录；本机构建记录位于 `desktop/.build/internal-release-test-components.json`，其中 `candidateRoot` 可用于本机验收。已接受的增量底座另记于 `desktop/.build/internal-release-accepted-base.json`；记录用于追溯，不替代用户功能验收。已有完整安装器保持不变。

本机验证并确认内部推送后：

```powershell
npm.cmd run publish:internal
```

默认直接使用构建清单中与内置公告一致的版本说明；如传入说明文件，其内容必须与 `customer-release-notes.json` 的对应版本一致。发布脚本校验干净提交、组合检查记录、测试频道、版本及全部归档摘要，并在服务器切换后的公开清单读回通过后才报告发布成功。不能在更新说明中宣称尚未验证的能力。

兼容的组件更新在干净提交执行：

```powershell
npm.cmd run release:components
npm.cmd run publish:components -- "../release/components/test/unsigned-component-release.json" "../docs/releases/对应版本-internal.md"
```

组件构建保留经过校验的完整组合目录和四个按哈希命名的组件归档，不创建全量 ZIP 或安装器，不替换 v1 频道。上传只补服务器缺失归档；客户端只下载本机没有或不匹配的组件。组件清单记录业务版本、底座摘要、最低底座和数据模式；底座或数据模式不兼容时转向完整包。组件回退只恢复兼容代码组合，完整升级前备份本机数据，不自动降级数据库。源码、原始素材、业务数据和旧回滚证据均不由缓存流程清理。

首次安装或核实确实需要完整包时，使用显式例外入口：

```powershell
npm.cmd run release:internal -- --full
npm.cmd run publish:internal -- --full "../release/AI获客 V1.0版本-测试版-安装程序.exe" "../release/AI获客 V1.0版本-测试版-安装程序-版本清单.json"
```

完整包构建记录仍为 `desktop/.build/internal-release-test.json`。仅构建完整包并不会更新增量频道；同版本两种清单均提供且底座兼容时，客户端优先增量。旧电脑底座不兼容时先安装适用的完整包，再进入后续增量。底座改变时按实际兼容边界递增 `componentBaseVersion`，不能只改标签或关闭摘要检查。

**升级路径门禁。** 组件发布可使用同版本完整包，或使用已验证的兼容底座桥接包；不要求每次小更新都制作同版本完整包。桥接包的签名清单必须包含与实际包内能力文件一致的 `componentBase.updateProtocol=4`、底座版本/摘要及数据模式，最终组件必须完全兼容。旧客户端由维护服务先提供底座，具备新能力后再提供最新组件；底座完成提示不能冒充目标组件已经安装。首次验证完整包仍下载并核对 SHA-256；后续只对同一摘要、同一签名 payload 的本机验收记录复用，并核实远端引用及 HEAD 可用性。维护服务须先支持桥接路由与 HEAD，旧服务失败时门禁关闭，不静默跳过。

**启动与空间。** 按用户 2026-10-20 补充要求，新底座安装／更新准备及更新后首次启动完整校验，真实页面就绪后保存成功版本记录。版本清单、签名清单及安装目录身份未变且上次启动正常时，复用记录，不再逐文件校验启动代码、运行时和示例。签名及清单结构仍检查；缓存缺失、清单变化、更新中断、未完成启动或本地服务异常时重新完整检查。缓存不承担检测两次启动间任意外部文件改写的职责，不能宣称与每次全文哈希有同等篡改检测能力。组件层不能替换固定启动器，本次策略需要一次新完整底座，之后继续组件增量。成功版本保留当前＋一代回退及一个完整候选；已登记的待回收副本在下一次正常启动后或更新时重试。SQLite 检查在隔离副本进行，不用文件字节变化直接判数据丢失，也不忽略业务行变化。原素材、成片、授权、回执不属于更新垃圾。

构建前估算单份目标程序及暂存空间，重试已有回收登记；空间不足先停止。空间账分别记录逻辑占用（硬链接去重、跳过链接目录）、阶段观测峰值、净变化、上传、本机下载及未知的远端 CI 产物。整盘空闲变化包含其他程序，不能全部归因于本次版本。历史存量必须列出具体候选及依赖后另获删除确认。

**更新成功后的自动保留。** 组件保留当前、一代回退及一个有效候选；完整更新确认后轮换自动备份，手动独立备份、未确认失败证据及其依赖继续保护。删除前整批核验快照，将不同于保留快照的历史资料按内容摘要保全到用户目录 `data/cloud-maintenance/preserved-backup-data`，保全回执落盘后才删旧副本；共享目录必须先完成所有相关记录的保全。保全失败或文件占用记录具体原因，正常页面就绪后由后台线程重试，组件回收不依赖完整备份是否刚被删除。Windows正在运行的底座可能与旧组件共享EXE硬链接，遇占用时登记保留；普通退出后复用已有、身份及摘要通过核验的独立更新助手，在父进程退出后调用原回收器，不另复制程序、不杀进程，更新交接期间不并发启动退出清理。成功启动但确认时锁冲突的完整更新，通过对应任务的完成状态及同版本启动回执恢复核验，不能仅凭版本较新删除备份。保全库不再次纳入完整更新备份，也不自动轮换；独有业务历史仍可能合理增长，不承诺总占用永远不变。

需要指定已有安装目录作为底座时，例如 1.1.30 已验收完整包：

```powershell
npm.cmd run release:internal -- --base "C:/path/to/accepted-test-app"
```

该命令成功生成增量候选后会登记底座版本、指纹和绝对路径；以后直接运行 `release:internal`。底座目录不得移动、覆盖或清理，记录与清单不一致时构建立即停止，不能静默改用别的目录。

2026-09-12 之前执行 `release:internal` 默认生成整包；历史发布记录中的旧命令按当时行为理解。已发布 1.1.20 的整包及公告保持原样，本次发布工具调整从下一次递增版本的构建开始使用。

如果安装后发现问题，保留现场、停止推广，基于修复后的代码增加版本号重新发布。客户端拒绝降低版本或序号，不通过手改服务器指针强行降级。旧安装包、数据库备份和签名历史按明确清理范围处理。

## 什么算完成

构建与发布入口会写入 `desktop/.build/space-usage/` 阶段空间报告。它记录本地观测峰值、净增量和成功上传文件字节数，不替代验收记录；本机下载与云端 CI 产物量没有证据时保持未知。统计范围、重叠报告与清理规则见 [开发与发布空间记录](development-storage.md)。

如果打包后仅调整 CI 编排或不进入包的自检夹具，可以保留已通过验收的安装包：记录包提交和最终 CI 提交，核对两者差异仅限这些文件，并验证已安装源码、运行时及 EXE 与包一致。发布仍从包对应的干净提交执行。应用源码、依赖、资源或运行时发生变化时必须重新构建及验收，不能用 CI 通过替代新版包验证。

| 状态 | 必须有的证据 |
|---|---|
| CI 通过 | 对应提交的 Actions 成功结果；本地命令通过单独记录 |
| 候选包通过 | 同一干净提交的完整打包检查、安装包版本清单及 SHA-256 |
| 本机可用 | 安装后的实际版本、数据保留及本次关键流程检查 |
| 内部 CD 完成 | 服务器读回有效签名清单，版本与已验收安装包一致 |
| 其他电脑更新完成 | 对应电脑已安装新版的实际确认或可信运行记录 |

CI/CD 不会自动证明所有微信场景、任意素材的视频质量或跨机器稳定性。完整商业发布的额外条件见 `README.md`、`PROJECT_STATUS.md` 和 `server/maintenance/README.md`。

## 发布规则（2026-09-24 从 AGENTS.md 原样挪入）

- 日常内部更新统一优先走组件增量：`npm.cmd run release:internal` 构建增量候选，验收后 `npm.cmd run publish:internal` 发布；原 `release:components`／`publish:components` 入口继续兼容。首次安装、已核实的底座／数据模式不兼容或明确要求离线安装器时才用 `--full`，不能因改动多、普通构建失败或习惯操作就改成整包。先核对基础文件差异；相同内容的压缩包排列变化不能当作依赖升级。增量仍需同提交检查、组合目录与实际切换验收，详细命令和例外见 [内部更新标准](docs/internal-release.md)。
- 每次发布须在 `desktop/src/shared/customer-release-notes.json` 为该版本写明客户可感知的功能新增、问题修复及未验证项，不用“修复与体验改进”等空泛概括。整包与增量发布共用同一份内容，随安装包内置，确保离线或手动安装后也能查看；已发布版本不原地替换程序内容，新修复递增版本并补新公告。发布前核对公告、版本、构建及验证证据一致，真实微信待测项不能写成已解决。
