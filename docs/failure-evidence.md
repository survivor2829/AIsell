# 微信失败诊断

## 1.2.11 内部诊断（2026-10-23）

内部测试版及开发版自动开启本地详细记录，普通日志与云端订阅仍使用原脱敏通道。`internal-diagnostics.jsonl` 保留微信模块阶段、异常消息和调用栈、原始失败结果、任务/运行/trace 关联和单调耗时；每条记录带版本及构建信息。文本过滤 API Key、令牌、认证头、Cookie、私钥等凭据，业务内容按本次内部排障授权保留。每份日志最多 5 MiB，最多 20 份，超大字段明确记录截断。

故障取证仍只截当前前台微信窗口，不激活、点击或发送。内部模式的 `internal_visible` 原始画面不再整窗涂黑；正式配置保持 `full_content` 遮罩。主进程直调和 CLI 驱动共用运行目录及取证开关。底层 worker 的 trace、脚本摘要、退出状态、输出尾部及实际异常进入本地详细记录，可区分 PowerShell 启动、窗口定位、读回和发送核验阶段。

现有“导出诊断包”统一包含两类日志、失败 JSON/PNG、任务护照和导出时的微信队列/占用/任务状态。`summary.json` 的 collection、coverage、truncation 明示读取失败、坏行、轮转缺口、文件/总量上限和截图未完成；单个坏行不会再让整批近期日志丢失。任务护照优先保留最新文件，导出前最多等待截图 1.5 秒。状态、日志和截图不是同一时刻的原子快照。

精准触达修正图片读回、计时及重复恢复，保留已发送文字回执；自动回复将发送状态落盘设为点击前的必需步骤，保存失败即停在发送前；朋友圈发布及互动保留底层失败及核验不一致的依据。身份核验和未知结果不补发规则不放宽。

旧诊断包中没有采集的证据无法补录，无法保证任意故障仅凭一包就确定唯一根因。新版应在问题复现后立即导出；先按版本/run/trace 对齐，再查具体异常、阶段和任务回执。故障机微信 4.1.15.13 与不同版本的实际图文送达仍待授权范围内验收；CI/CD 结果单独记录在发布报告。

以下为原诊断实现及历史验收记录；截图模式以本节内部/正式配置区分为准。

## 查什么

- `reason` / `code`：原有业务原因码，保持兼容。
- `rule_id`：固定源码位置编号。同一个原因码在不同条件下拒绝，编号不同。编号不要重排复用。
- `trace_id`：复用执行器已有 trace，关联输入、点击、发送前后检查。
- `evidence_id`：对应本地 JSON / PNG 文件名，不是联系人标识。
- `decision_scope=branch_not_task_outcome`：只代表某次分支拒绝，不等于联系人被跳过或整个任务失败。最终发送状态仍以原任务记录为准，不能从这个事件推断“未发送”。
- `input_read_exception_*`：具体草稿读取异常；`context_exception_*` 只是 PowerShell 错误队列上下文，不保证是当前拒绝的原因。

编号表：`desktop/src/shared/wechat-rule-catalog.json`。记录文件与行号；行号会随后续编辑漂移，定位应搜索固定编号。

当前包含五个窗口/朋友圈驱动中的 349 个固定拒绝位置、4 个不触发取证的默认占位值，搜索与回退使用 `search-r001` 至 `search-r024`、草稿读取 9 个阶段。并非声称整个仓库只有这些失败路径；未编号的其他业务异常仍保留原错误码。外部审查提到的“15 条拒绝”不代表所有模块总数。

## 存哪里、如何带回来

运行数据根目录下 `failure-evidence/`；从执行器的 `--data-dir` 上一级定位。先落 JSON，再截图，所以截图失败或超时不应抹掉拒绝编号。

吐槽中心反馈仍遵守服务端 20 条上限，其中优先保留最多 8 条近期相关拒绝记录，剩余保留既有诊断上下文。完整本地存证通过现有“导出诊断包”带出。默认不上传图片。

截图在内存中打码后才写盘，当前使用 `full_content` 保守模式：遮住整个内容区，仅保留最外侧边框和窗口尺寸。**不能用它检查聊天文字、OCR 识别结果或联系人身份**。未知窗口布局下，不以猜测的局部遮罩冒充可靠脱敏。

截图每个 PowerShell 进程最多一次，已有截图 5 秒内不再重复采集。每个拒绝仍有独立记录，`capture_status` 标明 saved / failed / throttled / pending。节流记录不伪称有截图。只接受前台微信进程，不激活窗口，不点击、不发送。

只保留采集器自己的 UUID 文件，最多 100 文件、20 MiB；导出读取最近最多 50 条事件。不保证无限历史。云端服务的新增字段白名单也须部署后才能保留新字段；只更新客户端不算完成云端验收。

## 验收

精准触达搜索证据（2026-10-22）：任务 passport 的 `raw-reading.json` 保留 `search_query_type`、`fallback_reason`，`search_attempts` 按首次、名字回退的顺序分别保存 `rule_id` 和脱敏 `ocr_observation`。观察只包含框坐标、字符分类、长度等结构，不包含搜索词、微信号或 OCR 原文。`search-r014` 仅指无法解释的本地候选；新增 `r019`–`r024` 分别区分微信号区域无法确认、超长微信号、多个精确名字行、缺少前置联系人标题、跨搜索分区、危险文字。

`search_result_not_opened` 的 `title_comparison` 从实际右侧标题生成长度、`sha256_16`、精确一致及仅标点/空白/全半角差异的摘要；归一差异只用于排查，不参与放行。`r015` 使用关闭弹窗前同次 OCR 的弹窗截图；该截图不可用时记录 `screenshot_unavailable`，不补拍关闭后的整窗冒充弹窗。本文不改变现有截图保留、打码策略；任务卡第 6 条仍等待用户决定。

本地定向检查覆盖编号唯一性、合成图像打码、采集节流、日志脱敏、反馈字段与导出；朋友圈及精准触达现有回放检查原判断不变。没有向真实联系人发消息。

异机须运行包含本次改动的版本，再复现一次并导出诊断包；旧版本不会凭空新增这些记录。先据 `trace_id` 对齐阶段，再看 `rule_id` 和具体异常，最后查原任务的发送状态。不能仅凭截图或一条拒绝事件宣称根因已确定或故障已修好。

## 排查与修复原则（2026-09-24 从 AGENTS.md 原样挪入）

- 故障先按设备、版本和执行阶段核对日志，区分已确认原因与待验证假设；保留具体原因及发送状态，不把不同错误统一成一个通用报错。
- 修复时沿故障步骤检查前后链路及共用适配器的调用方，修正有证据的同类假设，不只修入口，也不无依据扩大重写。验证覆盖实际触发条件（如最小化、空控件树、不同剪贴板内容），不只验证预先准备好的顺利场景；故障机复验结果按用户实际确认范围记录，再沉淀通用规则。

## 已定位根因的标准与飞行记录仪（2026-10-29 用户决定）

客户电脑上的报错，只有同时满足下面三条才允许改业务代码；任何一条做不到都是“证据不足”。证据不足时，下一步只发补取证的更新，不凭猜测改代码，也不请客户导出诊断或截图。

1. **证据**：现场包里有失败那一步和之前几步的画面、识别结果，能说明程序“看到了什么、怎么判断的”。
2. **复现**：在开发机上，用现场包里的输入重跑**当前代码**的识别/判断函数，得到同样的错误（`npm.cmd run issues:replay -- <编号>`）。
3. **验证**：修复后，同一份输入得到正确结果。用 `--keep` 保存为现场回放用例，`issues:verify` 与 `release:internal` 之后每次都重跑；结果有变化时只提醒，不拦截发版。

`npm.cmd run issues:show -- <编号>` 打印逐步记录，并直接判定“证据完整”或“证据不足：缺……”。聚类只用来排优先级；同一错误码下可能混着不同根因，每类都要拿代表性现场单独证实。

**飞行记录仪**：仅在内部诊断配置下开启，即测试版的 test 数据配置；正式版不开启。目录为 `XIAOXI_FLIGHT_DIR`，在用户目录下的 `data/flight-recorder`。
- **每一步记一帧**：朋友圈每一帧画面、自动回复每一帧画面，两帧之间至少间隔 0.4 秒；保存为 JPEG，长边不超过 1600 像素。
- **可回放的识别**：朋友圈菜单识别保存无损 PNG 原图，以及识别的输入（视口、头像、局部范围）和输出（候选、计数），供 `issues:replay` 原样重跑。
- **文字识别**：每次识别的文字和位置。
- **失败那一刻**：微信报错写入日志约 3 秒后，主进程另起一个取证进程，拍所有显示器的整屏，记录全部可见窗口（标题、类名、位置、进程、是否前台）和微信控件结构树（深度不超过 8 层、最多 500 个节点）。1 分钟内已经拍过就不重复拍；环境原因不拍。
- **为什么单独一个进程**：每个微信操作脚本都带同一段公共开头。2026-10-29 本机实测，公共开头里一旦有整屏截图和窗口标题枚举，Defender 就把剪贴板脚本判为恶意并拦截，而被拦的脚本会让微信任务本身失败。所以公共开头只保留“存当前帧、记识别结果”；`worker-antivirus.self_check.cjs` 检查公共开头里没有截屏或窗口枚举，并逐个解析全部操作脚本。取证进程自己被拦时只是少一张截图，不影响任务。

本机只保留 2 小时、最多 120MB。现场包生成时复制失败前 10 分钟内最多 30 步，以及同一时段的任务护照（真实截图、原始读取、预期），作为附件随现场包上传。服务器只有管理端能看，30 天删除。

上面这些都开启时，非内部配置下涂灰的截图不再作为证据上传。

环境原因（`wechat-failure-policy.cjs` 判为 environment，如客户正在使用微信）由软件自己处理，只计数，不生成现场包。同一台电脑一天内同一原因到第 5 次时，才按“可疑 bug”生成一个现场包。

**闭环确认**：微信任务完成时上报 `wechat_workflow / task.succeeded`（只含任务类型和进度）。`issues:pull` 对每类问题按电脑统计：更新到更高版本后同类任务已跑通、更新后仍复发、还没有更新后的记录。不自动重做任务。

**第 3 期（2026-10-29）**：
- `issues:pull` 日报的“版本健康”按最新版对比上一版，看哪类任务失败占比变高、哪些错误第一次出现，作为优先修复的依据。新版有问题就修复后发新版，不暂停推送（用户决定）。
- `npm.cmd run issues:code -- <码>` 打印错误码地图：类别、当前源码里的全部抛出位置、定位要看的证据、能否本机复现。地图每次从源码现算，不维护手写清单，也不设 CI 登记门禁。
