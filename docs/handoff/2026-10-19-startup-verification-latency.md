# 启动校验延迟修复

## 范围与状态

- 基线 main `268ed85`，本机已发布1.1.96。修改仅涉及启动引导计时、组件文件校验及对应定向自检；没有修改配音、人物生成、字幕、详情图业务或原始资料。
- 源码修复和安装程序诊断进程验收已完成。**未重新完整打包、未发布，已安装1.1.96文件保持原样，重启后仍使用旧校验器。** 本次新校验器只在受控安装程序进程内替换函数以验证真实入口，不是已部署补丁。
- 这两个实现文件在 `desktop/component-layout.json` 明确归属固定 `base`。普通应用组件无法更新安装目录中的引导程序；正式安装修复需要下一次有授权的底座更新。不能只发应用增量然后宣称老客户端已修复，也不通过改本机签名清单绕过更新保护。
- 任务开始时 `PROJECT_STATUS.md` 和 `docs/handoff/2026-10-19-video34-release-result.md` 已有上轮未提交记录，原样保留，不混入修复提交。没有修改其他工作树。

## 根因与证据边界

正常安装入口：`bootstrap.boot` → `verifySelected`（验签、兼容及目录清单检查）→ `verifyGeneration` → `verifyFiles` → 加载主程序。旧 `verifyFiles` 对每个文件串行重复查询所有父目录，再额外stat并读取完整文件哈希，导致首次界面必须等待成千上万次磁盘往返。

本机1.1.96包含4,086个文件、1,631,303,383字节。旧校验产生30,324次lstat、4,086次stat、563次readdir及4,086次完整哈希。重复目录查询和完全串行读取把文件系统响应波动累加到首屏之前。

- 既有慢启动日志：main_loaded 46.138秒，login_interactive 48.163秒；另一次28.898/30.744秒。云端会话完成在主程序加载之后，没有证据把这两次长等待归因于云端请求。
- 原版独立全量校验6.470秒；原版实际Electron入口的校验8.677秒，其中lstat约4.177秒、stat约0.605秒。
- 原慢启动没有逐项I/O日志，因此不能声称已证明当时46秒的每一秒来自哪种设备等待，更不能无依据归因于杀毒软件。已明确并修复的是前置全量校验中的重复串行I/O瓶颈；补计时后可继续追踪真实冷启动。

## 修改

- 每轮校验只检查一次共享父目录，缓存不跨启动、不缓存文件哈希。文件仍逐个检查类型、大小和完整SHA-256；签名、清单一致性、额外文件及链接拦截保留。
- 最多四个文件读取并行，限制磁盘和内存占用。失败后不再排新文件，等待在途读取结束再向更新器报错，避免清理暂存目录时仍有读句柄。
- 复用现有启动日志，补充bootstrap_loaded、component_verification_started/finished三个阶段。

## 测量与验证

| 测量口径 | 原实现 | 修复后 |
| --- | ---: | ---: |
| 同一安装目录、4,086文件全量校验（Node） | 6.470秒 | 1.599秒 |
| Electron实际引导校验 | 8.677秒 | 2.086—2.443秒 |
| 文件属性查询 | 34,410次 | 4,649次 |
| 完整文件哈希 | 4,086次 | 4,086次 |
| 修复后到可操作登录页 | — | 4.046/4.551秒 |

这些是本机实测，不是对所有磁盘或所有冷启动的时间保证。为验证延迟放大机制，另取64个相同小文件，对每次属性查询施加标称1ms延迟：旧实现8.415秒，新实现0.474秒；Windows实际定时器唤醒约15ms，故该实验只证明对I/O延迟敏感度的差异，不冒充真实全量启动。全量注入实验因定时器粒度耗时过长已中止，没有用其未完成结果下结论。

- 旧实现运行新增性能回归明确失败（同目录被重复检查7次）；修复后组件更新8项自检、bootstrap自检及CJS语法检查通过。没有新增界面改动，因此没有重复界面构建或完整包构建。
- 定向覆盖同大小内容篡改、根目录/父目录junction、缺失文件、额外文件、签名/兼容性、失败读操作收尾；没有放松任何原有失败断言。
- 安装程序诊断进程使用原安装EXE、原已保存授权和原数据：登录、内容/详情图服务ready、检查更新current、两条离线样片播放/拖动/关闭、数字人页面、详情图历史恢复通过。

- 已完成限定四个修改文件的复用、质量与效率独立只读复查，无新增阻断。未新增付费调用、微信操作或系统设置修改。
