`desktop/scripts/update-install-acceptance.ps1` 只允许 GitHub 托管 Windows 或 Windows Sandbox 身份，安装原始 1.1.64，再通过正式官方助手安装官方 1.1.86。使用合成回执与运行时 junction，不上传本机客户资料。目标必须安装成功并收到 1.1.86 启动 ACK。

原包和助手保存在未发布草稿 `acceptance-original-64-20261012`，不是客户更新发布。目标包从官方 HTTPS 获取，固定 CA 并复核摘要。GitHub 读取未发布草稿需要写权限，仅手动验收 job 获取该权限，没有发布步骤。

验收工具首次遇到草稿读取权限不足，随后遇到 UIAutomation 控件不支持 InvokePattern、按钮类型无法定位；均未执行新版安装，不能当作产品安装失败。已在本机只读核对真实 WinForms BUTTON 句柄，改用按进程核验的原生按钮消息。

正常升级与故障验收使用不同并发组。故障组分别中断正式安装器（观察到程序已发生变化后）、中断新程序启动，要求恢复旧程序的逐文件摘要、版本选择记录和原回执，并重新打开旧程序。这是隔离机器上的受控实际进程故障，不等同已复现客户电脑的 EPERM。

原正式助手在独立验证机成功执行原始 64 安装，但在交接安装前停止；运行 `38289563337` 记录故障 `update_failed`，C 盘仍有约 28.4 GiB 可用，不能归因为空间不足。已增加仅包含故障类别及模块行号的本地诊断，不记录原始异常文本、业务内容或凭据；新诊断助手暂存在未发布草稿，SHA-256 `83d9fe9eee4fc6a246b95e00e042c5547dacf6fb607b3bbf4d4e9ae7491b5aba`，不是正式分发助手，也未改变更新频道。

普通源码 CI `38288777039` 已通过：源码自检、运行与密钥边界、测试与交付界面构建，以及服务/内容检查。该运行早于诊断代码补充，不代表最新诊断提交或真实安装通过。真实安装及故障结果待对应运行完成后补入，当前不标记通过。
