# 自动保留机制修复

基线 dc5e112（已发布 1.1.99）；本轮只修改更新清理链路，不改生成业务、音色和素材。最终1.1.101已安装并发布，详见末节。

发现与修复：
- 旧备份退役前原来只核验新备份，没有保全旧备份的独有内容。新增内容摘要去重保全及可恢复回执，全部共享集合先保全再删除；失败继续保护原副本。
- 正常启动只在成功移除完整备份时才收集旧组件。现在真实页面就绪后用既有 worker 独立重试组件与备份，避免阻塞首屏。
- 数据检查暂时失败会留下同版本待确认目标；helper 完成后遇注册表锁冲突，还可由原任务完成状态与 ACK 恢复确认。未成功启动、其他版本、未分类历史和主动手动备份不自动采用。

验证：
- 备份治理定向自检通过：连续确认后仅一代自动已确认备份，旧数据库字节保全，手动备份与外部目录保护，错误版本不确认，同版本恢复确认，完成 ACK 丢失确认窗口恢复，共享目录和 EBUSY 隔离重试。
- 新保全断言对基线源码失败（旧数据已删除但保全回执不存在），修复源码通过。
- 组件更新定向检查覆盖签名、损坏文件、候选轮换、升级及失败回收；源码语法检查通过。以最终执行结果及 CI 为准。
- 独立只读审查指出的确认锁竞争、共享目录先删后验两项已修复并定向回归，复查无阻断项。

边界：上述是修复阶段记录；最终安装与发布结果以末节为准。本轮未重新完整打包、未新增付费调用或真实微信发送。独有历史资料自身仍可能增长，去掉的是重复完整备份的无界累积。

发布兼容调整：首次1.1.100组件构建识别update-helper/update-retention为固定底座文件，安全门禁拒绝。两文件恢复原字节，启动重试编排放在应用组件update-startup-maintenance worker，继续调用原底座回收器；不变更底座分类或签名校验。调整后组件与备份定向回归通过。

1.1.100本机候选发现真实退出占用：旧1.1.98 EXE与安装底座/current/previous共享inode，Electron32删除抛EPERM；开发Node24在相同条件可unlink，原fixture未覆盖该差异。新增真实Electron定向场景，复用已完成更新的独立helper在正常退出后运行原回收器，不复制程序、不杀进程。实际正常入口进程43864退出后旧98成功回收，见outputs/update-retention-20261020/exit-fix-actual.json。最终发布递增1.1.101，100未对外发布。
