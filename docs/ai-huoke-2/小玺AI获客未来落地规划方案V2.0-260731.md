# 小玺 AI 获客未来落地规划方案 V2.0

> 基于 V1.0 原文、当前代码、项目状态和 2026-07-31 运行日志重新校准  
> 版本日期：2026-07-31  
> 产品主线：内容获客 → 微信承接 → 学员分发 → 线索与成交复盘

## 一、一句话结论

小玺 AI 获客下一阶段不是把主动触达、自动回复、朋友圈互动和朋友圈发布写成一段互相调用的大程序，而是让每项能力独立运行、独立保存进度、独立失败，再由“统一调度中心”按照事件、优先级和微信资源锁自动串联。

这样既能实现全流程自动化，也不会因为朋友圈的一个问题拖垮主动触达或自动回复。

近期目标不是直接运营 1,000 个账号，而是先完成三件事：

1. 收口微信拓客现有功能和安装版验收，解决启动抢占微信等问题。
2. 建成内容生产底座，先做课程拆条，再做智能混剪。
3. 建立总部生成发布包、学员本人手机确认发布、数据回传的试点闭环。

## 二、V1.0 保留什么、V2.0 修正什么

### 2.1 继续保留的方向

V1.0 的核心方向是正确的：

- 不推翻微信私域能力重做。
- 用短视频解决“客户从哪里来”。
- 用自动回复、主动触达和朋友圈运营解决“客户来了怎么接、怎么跟”。
- 先做好内容和人工确认发布，再逐步增强平台对接。
- 所有动作都要有任务、状态、日志和复盘数据。

### 2.2 必须纠正的状态口径

V1.0 把“素材库、3 条 9:16 草案、人工发布包、发布数据回填和线索回流”描述为短视频 1.1 已有能力。按当前仓库和 `PROJECT_STATUS.md` 的可验证事实，这些能力不能整体算作已经完成。

当前真实状态如下：

| 板块 | 当前可验证状态 | 仍未完成 |
|---|---|---|
| 联系人同步、自动回复、主动触达 | 核心开发及本机历史实测基本完成 | 当前正式安装版本的 exact-build 和异机回归 |
| 朋友圈逐帖互动 | 点赞和 AI 评论已有本机单轮历史验收 | 当前修复版的启动、到点、暂停和跨重启实机计时验收 |
| 朋友圈发布 | 尚无完整生产能力 | 编辑、审核、发布任务、结果确认和失败恢复 |
| 产品详情图 | 已集成受控本地 sidecar，离线上传、排版、PNG 导出和历史恢复已通过开发机检查 | 用户覆盖安装、净机和付费 AI 路由验收 |
| 素材与成片底座 | 已有原片原地索引、任务恢复、素材列表、缓存设置和成片中心基础结构 | ffprobe 净机能力、转录、镜头分析、时间线和渲染 |
| 课程拆条 | 尚未实现 | 选段、竖屏重构、字幕、包装和审核 |
| 智能混剪 | 尚未实现 | 脚本拆镜、素材语义匹配、时间线和稳定重渲染 |
| 渠道运营 | 已确定合规方向和界面结构 | 学员、账号、发布包、回执、线索回流和数据复盘服务 |

V2.0 以后统一采用三个状态：`已验证`、`开发中`、`规划中`。页面占位、方案文字和历史原型不再计作已完成能力。

## 四、目标业务闭环

```text
启动 AI 获客
→ 只恢复状态和定时，不打开微信、不进入朋友圈
→ 统一调度中心判断当前任务和资源
→ 主动触达
→ 发现联系人新消息
→ 在安全检查点暂停主动触达
→ 自动回复
→ 回复结果确认
→ 继续主动触达剩余联系人
→ 达到设定时间或批次条件
→ 朋友圈点赞与评论
→ 朋友圈发布
→ 记录结果、线索和异常
→ 进入下一轮或结束今日任务
```

内容侧的闭环是：

```text
素材仓库
→ AI 分析
→ 课程拆条 / 智能混剪
→ 可编辑初剪
→ 字幕、竖屏、品牌包装
→ AI 检查 + 人工终审
→ 成片中心
→ 生成发布包
→ 学员本人发布
→ 回传链接和数据
→ 线索进入微信客户池
→ 自动回复和主动触达承接
```

## 五、解耦但保持自动化的技术架构

### 5.1 统一调度中心

统一调度中心只做五件事：

1. 接收事件。
2. 判断优先级。
3. 下发任务命令。
4. 申请和释放资源锁。
5. 记录流程状态。

它不直接识别微信窗口、不生成回复、不点赞、不剪视频。具体执行仍由各自模块完成。

### 5.2 独立执行模块

| 模块 | 接收的命令 | 对外事件 | 独立状态 |
|---|---|---|---|
| 主动触达 | 开始、暂停、继续、结束 | 联系人开始、发送确认、批次完成、结果未知 | `active_touch/` |
| 自动回复 | 开始监听、处理消息、暂停 | 新消息、回复完成、需人工、结果未知 | `auto_reply/` |
| 朋友圈互动 | 到点执行、继续剩余、暂停 | 帖子完成、目标完成、需人工 | `moments/` |
| 朋友圈发布 | 创建草稿、请求审核、确认发布 | 审核通过、发布确认、结果未知 | 独立发布状态 |
| 内容生产 | 分析、拆条、混剪、渲染 | 候选完成、渲染完成、素材不足 | `content-engine/` |
| 渠道运营 | 分配发布包、催办、确认回执 | 学员领取、发布验证、线索回传 | 服务端独立状态 |

模块之间不得直接调用“下一个模块”。例如主动触达不能直接启动朋友圈；它只发出“批次完成”事件，由调度中心决定是否进入朋友圈互动。

### 5.3 事件总线

首期可先在 Electron 主进程内实现轻量事件总线，不急着上复杂中间件。事件至少包含：

- `event_id`：唯一编号。
- `event_type`：事件类型。
- `task_id`：所属任务。
- `occurred_at`：发生时间。
- `source`：来源模块。
- `payload_summary`：不含联系人原文和密钥的最小摘要。

重要事件落盘，应用重启后可重放“尚未处理”的事件，但发送、评论、发布等结果未知事件绝不能自动重做。

### 5.4 微信资源仲裁器

同一时刻只允许一个模块控制微信前台窗口。资源状态建议统一为：

```text
free
user_busy
auto_reply
active_touch
moments_interaction
moments_publish
manual_review
```

获取资源锁前必须说明任务、阶段和超时策略；释放时记录结果。内容转录和视频渲染使用另一套 CPU、磁盘资源队列，不能占用微信锁。

## 六、优先级和抢占规则

从高到低：

1. 用户正在手工操作微信。
2. 收到联系人新消息，需要自动回复或人工接管。
3. 已经开始且必须完成结果确认的单次原子操作。
4. 主动触达。
5. 朋友圈互动。
6. 朋友圈发布。
7. 后台素材分析和视频渲染。

具体规则：

- 主动触达不是在任意一毫秒强行停止，而是在“当前联系人结果已确认、下一个联系人尚未开始”的检查点暂停。
- 如果已点击发送、评论或发布，必须先确认成功、失败或结果未知，再释放资源。
- `outcome_unknown` 一律进入人工确认，不得自动补发。
- 朋友圈失败只暂停朋友圈模块，不得让自动回复或主动触达整体进入故障状态。
- 内容渲染负载过高时自动降并发，不能让微信识别和界面失去响应。

## 七、启动、暂停和恢复规则

### 7.1 软件启动

启动状态固定为：

```text
initializing → restoring → idle / waiting
```

强制规则：

- 启动只读取任务、进度、下次时间和资源锁。
- 不得因为初始化而自动前置微信、打开朋友圈、点击入口或发送内容。
- 未来仍未到点的任务恢复原定时。
- 已错过时间的朋友圈任务保存为“待续跑”，保留今日完成数和帖子去重记录。
- 当前安全版由用户点击“立即执行今日剩余”后继续；V2 调度中心完成后，可在用户主动开启“托管模式”时，经过可配置的启动缓冲期、确认用户未操作微信并成功取得资源锁后自动续跑。

### 7.2 暂停与继续

所有业务采用统一状态：

```text
queued
→ running
→ pausing
→ paused
→ resume_pending
→ running
→ completed

异常分支：
failed_retryable
failed_manual_review
outcome_unknown
cancelled
```

“继续之前任务”必须明确到哪个粒度：

- 主动触达：从尚未处理的联系人继续，不重发已确认联系人。
- 自动回复：按消息唯一标识去重，不重复回复已确认消息。
- 朋友圈互动：保留当日完成数和帖子指纹；首期不能精确恢复关闭前滚动位置。
- 朋友圈发布：保存草稿版本和发布任务唯一编号；结果未知不重新发布。
- 视频任务：从已完成的代理、转录、镜头分析或渲染阶段继续，不从头扫描原片。

## 八、内容生产方案

### 8.1 共用素材底座

- 原始视频、图片和音频保持在用户硬盘原位置，不重复复制几十 GB 原片。
- 保存路径、大小、修改时间、抽样指纹、时长、分辨率、来源和授权状态。
- 生成可重建的代理、音频、缩略图、关键帧、字幕和场景索引。
- 缓存目录由用户选择，设置容量上限和低空间保护。
- 索引、转录、分析和渲染都可暂停、恢复和取消。
- 产品详情图输出可一键登记为素材，继续用于智能混剪。

### 8.2 课程拆条优先

适用于 10–40 分钟导师课程、会议和客户沟通。

首个 MVP：

1. 转录并生成词级时间戳。
2. 按完整观点寻找 3–8 个候选。
3. 默认每段 30–90 秒，避免半句话截断。
4. 自动生成 9:16 画面、字幕、标题、关键词高亮、Logo 和 CTA。
5. 提供开头、结尾和字幕人工修改。
6. 输出 1080×1920 视频和封面。

验收重点不是“完全替代剪辑师”，而是让运营人员拿到精美、可快速修改的初剪。

### 8.3 智能混剪其次

适用于碎片口播、产品视频、图片和产品详情图。

首个 MVP：

1. 用户输入脚本，或由 AI 根据选中素材生成脚本。
2. 把脚本拆成镜头意图、口播、字幕和 CTA。
3. 按文本、画面、产品、城市和授权范围检索素材。
4. 控制镜头重复率、节奏和画面多样性。
5. 素材不足明确标红，不虚构产品性能和客户案例。
6. 输出可编辑时间线，替换镜头后可稳定重渲染。

### 8.4 AI 生成视频

先保留供应商适配层，不在首期绑定 Seedance 或其他单一模型。只有官方 API、价格、商业授权、肖像与 AI 标识要求确认后再开放。

## 九、朋友圈发布与渠道运营

### 9.1 朋友圈发布

朋友圈发布不能直接接在互动函数末尾。它是独立任务，至少包含：

```text
draft
→ waiting_review
→ approved
→ publishing
→ published_verified / outcome_unknown / rejected
```

首期先做草稿、图片/视频检查、文案预览和人工确认；自动发布必须在真实微信版本上单独验收。

### 9.2 学员账号矩阵

首期采用“总部内容工厂 + 学员本人发布”：

1. 总部生成差异化发布包。
2. 学员打开安全链接或轻量 H5。
3. 预览、下载视频和封面，复制文案。
4. 学员用本人手机发布。
5. 粘贴链接或上传截图回传。

不收密码、验证码、Cookie 或设备登录态，不做群控和模拟点击。官方 OAuth 发布以后逐平台申请和审核。

扩容顺序：

| 规模 | 目标 |
|---|---|
| 10–20 个账号 | 人工终审，连续运行 4 周 |
| 50 个账号 | 上线 H5、排期、催办和回执 |
| 300 个账号 | 云端控制面、租户隔离、对象存储和多渲染节点 |
| 1,000 个账号 | 只有平台合规、产能、发布率、违规率和线索转化达到门槛后再进入 |

## 十、数据、日志和经营指标

### 10.1 核心数据

- `WorkflowRun`：一整套自动化流程。
- `TaskRun`：某个模块的一次任务。
- `Checkpoint`：可恢复进度。
- `AutomationEvent`：模块间事件。
- `ResourceLease`：微信或内容资源锁。
- `Asset`、`ContentProject`、`TimelineV1`、`RenderJob`。
- `PublishPackage`、`StudentProfile`、`ChannelAccount`、`ConsentRecord`。
- `Lead`：来源平台、视频、活动和后续微信承接状态。

### 10.2 日志要求

日志必须区分：

1. 只恢复状态。
2. 进入等待队列。
3. 获得微信控制权。
4. 真正打开微信或朋友圈。
5. 尝试动作。
6. 成功、失败或结果未知。

不得记录联系人消息原文、客户隐私、平台 token、API Key 或完整脚本文案。

### 10.3 经营指标

- 主动触达成功率、结果未知率、人工接管率。
- 自动回复首响时间、有效回复率、转人工率。
- 朋友圈任务完成率、重复拦截率、异常率。
- 课程拆条首稿可用率、单条人工修改时间。
- 智能混剪脚本镜头覆盖率、镜头替换次数、渲染成功率。
- 发布包领取率、实际发布率、违规率。
- 有效线索率、加微率、跟进率、成交率和单条内容成本。

## 十一、主要风险与控制

| 风险 | 强制控制 |
|---|---|
| 启动抢占微信 | 启动只恢复状态；真正执行必须经过调度和资源锁 |
| 模块高度耦合 | 事件驱动；模块不能直接启动下一个模块 |
| 自动回复与主动触达冲突 | 新消息优先；当前原子动作收尾后暂停触达 |
| 重复发送、评论或发布 | 唯一任务号、检查点、结果三态；未知不重做 |
| 单模块故障拖垮全局 | 独立状态、独立重试、熔断和人工处理队列 |
| 素材版权和肖像声音争议 | 保存来源、用途、期限和授权；无授权不得进入成片 |
| AI 虚构宣传 | 产品参数和案例来自事实库，敏感宣传人工终审 |
| 账号被接管或封禁 | 不收账号密码和登录态；本人发布或官方授权 |
| 大量账号内容雷同 | 跨账号相似度检查，真实城市、服务和素材差异化 |
| 磁盘或费用失控 | 缓存上限、低空间停止、任务预算和付费二次确认 |
| 千账号数据串线 | 租户隔离、最小权限和审计记录 |

## 十二、实施路线

单人开发情况下，V1.0 的 90 天同时完成内容、成片、发布、回流和完整 AI 员工过于激进。V2.0 采用“基础版目标 + 拉伸目标”。

| 阶段 | 预计时间 | 主要工作 | 完成门槛 |
|---|---:|---|---|
| 0. 基线收口 | 1–2 周 | 启动唤醒修复、新安装包、微信 exact-build、产品详情图覆盖安装 | 源码、包和实机证据同版本 |
| 1. 调度中心 MVP | 2–4 周 | 事件总线、统一任务状态、微信资源仲裁、暂停恢复 | 自动回复可打断触达并安全恢复；模块故障隔离 |
| 2. 课程拆条 MVP | 6–10 周 | 转录、选段、竖屏、字幕、包装、审核 | 5 个长视频样本，每个输出 3–8 个候选，90% 以上不截半句话 |
| 3. 智能混剪 MVP | 6–10 周 | 脚本拆镜、素材检索、时间线、渲染 | 20 个混合素材项目可编辑并稳定重渲染 |
| 4. 朋友圈发布 | 2–4 周 | 草稿、审核、发布状态、结果确认 | 单账号连续运行，无结果未知自动重发 |
| 5. 分发试点 | 4–6 周 | 学员 H5、发布包、回执、线索回流 | 10–20 个账号连续 4 周，发布完成率达到 80% |
| 6. 规模化 | 达标后 | 云端控制面、多租户、官方平台适配器 | 先过 50 个账号门槛，再到 300 |

前 90 天的现实目标：完成基线收口、调度中心 MVP 和课程拆条可用版；智能混剪做到原型或早期 MVP。不能为了赶时间把未验收页面写成完成。

## 十三、验收标准

### 13.1 启动与调度

- 打开 AI 获客后，不出现由初始化触发的 `campaign.started` 或 `campaign.open_started`。
- 错过时间后显示“待续跑”，今日完成数和帖子指纹不丢失。
- 未来重试时间按原时间恢复，不提前执行。
- 用户手工操作微信时，所有自动化让路。
- 收到新消息后，主动触达在安全检查点暂停；回复完成后只继续剩余联系人。
- 任一模块失败不改变其他模块的已确认结果。

### 13.2 内容生产

- 导入 20–50GB 素材不复制原片，应用界面不卡死。
- 中断后从检查点恢复，清缓存不伤原文件。
- 课程拆条和智能混剪都输出可编辑初剪，不只输出一段不可修改的视频。
- 素材不足、无授权或事实冲突时明确阻断。

### 13.3 发布与渠道

- 无真实授权时只生成发布包，不自动发帖。
- 发布结果未知进入人工确认，不自动重发。
- 不保存学员密码、验证码、Cookie 和设备登录态。
- 每个发布包可追溯到素材、脚本、审核人、学员和版本。

## 十四、现在最合适的下一步

1. 先把本次“启动唤醒朋友圈”修复打入新的测试安装包，做一次打开、关闭、跨时间和继续剩余任务的真实验收。
2. 新建统一任务中心和流程编排层，只先接主动触达、自动回复和朋友圈互动三个现有模块。
3. 用 5 个真实的 10–40 分钟课程视频建设课程拆条 MVP。
4. 课程拆条稳定后，再用碎片口播、产品视频、图片和产品详情图做智能混剪。
5. 内容可用后再启动 10–20 名学员的发布包试点，不直接跳到多账号托管。
